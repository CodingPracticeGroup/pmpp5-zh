9.1 Background

A histogram is a display of occurrences of data values in a data set. In the most common form of a histogram, the value intervals are plotted along the horizontal axis and the frequency of data values in each interval is represented as the height of a rectangle, or bar, rising from the horizontal axis. For example, Fig. 9.1(b) shows the histogram of pixel intensity values of the grayscale image of a tree in Fig. 9.1(a). Grayscale images typically consist of pixels with intensity values ranging between 0 and 255 where 0 is black and 255 is white. The histogram in Fig. 9.1(b) splits this range into four intervals with 64 values each. The six black pixels depicting the trunk of the tree are counted in the range [0-63]. The 12 dark gray pixels depicting the leaves of the tree are counted in the range [64-127]. The 14 light gray pixels depicting the grass around the tree are counted in the range [128-191]. The 32 white pixels depicting the sky are counted in the range [192-255]. Histograms provide useful summaries of data sets. In our example, we can see that the image being represented consists of pixels that are heavily concentrated in the bright (higher) intensity intervals and lightly concentrated in the dark (lower) intensity intervals. Such a shape of the histogram is sometimes referred to as a feature of the data set and provides a quick way to determine if there are significant phenomena in the data set, such as if an image has low or high light exposure. As another example, the shape of a histogram of the purchase categories and locations of a credit card account can be used to detect fraudulent usage. When the shape of the histogram deviates significantly from the norm, the system raises a flag of potential concern. Many application domains rely on histograms to summarize data sets for data analysis. One such area is computer vision. Histograms of different types of object images, such as faces vs. cars, tend to exhibit different shapes. One can plot the histogram of pixel intensity values in an image or an area of an image, as we have seen. A histogram of the sky on a sunny day might have only a small number of very tall bars in the high-intensity intervals of the luminous spectrum. The process of computing histograms of image subareas is an important approach to feature extraction in computer vision, where a feature refers to a pattern of interest in images. In practice, whenever there is a large volume of data that needs to be analyzed to distill interesting events, histograms are likely used as a foundational computation. Credit card fraudulence detection and computer vision obviously meet this description. Other application domains with such needs include speech recognition, website purchase recommendations, and scientific data analysis such as correlating heavenly object movements in astrophysics. Histograms can be easily computed in a sequential manner. Fig. 9.2 shows a sequential function that calculates an image histogram. The C code assumes that the input image comes in the unsigned char array image where each element specifies the grayscale intensity of a pixel (line 01). Additionally, the histogram is to be generated into the unsigned int array bins (line 01). The number of pixels in the image is specified by the function parameters width and height (line 02). The for-loop (line 03) sequentially iterates over the image pixels. The image is treated as a 1D array of size width*height since the 2D indices of the pixels are not relevant to the computation. It loads the pixel value from the image (line 04) and increments the histogram bin corresponding to that pixel value (line 05). Here, we assume that each histogram bin represents a single pixel value. If the bins represent an interval of pixel values as in Fig. 9.1, then we would divide the pixel value by the interval width before indexing the array of bins. The C code in Fig. 9.2 is quite simple and efficient. The computational complexity of the algorithm is O(N ) where N is the number of input data elements. The image array elements are accessed sequentially in the for-loop so the CPU cache lines are well used whenever they are fetched from the system DRAM. The bins array is so small that it fits well in the level-one (L1) data cache of the CPU, which ensures fast updates to the bins elements. For most modern CPUs, one can expect that execution speed of this code to be memory bound, i.e., limited by the rate at which the data elements can be brought from DRAM into the CPU cache.

The most straightforward approach to parallelizing a histogram computation is to launch as many threads as input elements and have each thread to process one input FIGURE 9.3 Basic parallelization of image histogram.

element. Each thread reads its assigned pixel value and increments the appropriate bin for that pixel value. Fig. 9.3 illustrates an example of this parallelization strategy. Note that multiple threads may be assigned to pixels with the same value and need to update the same bin, which is a conflict referred to as output interference. Programmers must understand the concepts of race conditions and atomic operations in order to confidently handle such output interferences in their parallel code. An increment to an interval counter in the bins array is an update, or read-modifywrite, operation on a memory location. The operation involves reading the memory location (read), adding one to the original value (modify), and writing the new value back to the memory location (write). Read-modify-write is a frequently used operation for coordinating collaborative activities. For example, when we make a flight reservation with an airline, we bring up the seat map and look for available seats (read), we pick a seat to reserve (modify), and change the seat status to unavailable in the seat map (write). A bad potential scenario can happen as follows: • Two customers simultaneously bring up seat map of the same flight. • Both customers pick the same seat, say 9C. • Both customers change the status of seat 9C to unavailable. After the sequence, both customers thought that they have seat 9C. We can imagine that they will have an unpleasant situation when they board the flight and find out that one of them cannot take the reserved seat! Believe it or not, such unpleasant situation indeed happens in real life due to flaws in airline reservation software. For another example, some stores allow customers to wait for service without standing in line. They ask each customer to take a number from one of the kiosks. There is a display that shows the number that will be served next. When a service agent becomes available, the agent asks the customer to present the ticket that matches the number, verify the ticket, and update the display number to the next higher number. Ideally, all customers will be served in the order they enter the store.

An undesirable outcome would be that two customers simultaneously sign in at two kiosks and both receive tickets with the same number. When a service agent calls for that number, both customers expect that they are the one who should receive service. In both examples, undesirable outcomes are caused by a phenomenon called a read-modify-write race condition, where the outcome of two or more simultaneous update operations varies depending on the relative timing of the operations involved. Some outcomes are correct, and some are incorrect. Fig. 9.4 illustrates a race condition when two threads attempt to update the same bins element in our image histogram example. Each row in Fig. 9.4 shows the activity during a time period, with time progressing from top to bottom. Fig. 9.4(a) depicts a scenario where Thread 1 completes all three parts of its readmodify-write sequence during time periods 1 through 3 before Thread 2 starts its sequence at time period 4. The value in the parenthesis in front of each operation shows the value being written into the destination, assuming the value of bins[x] was initially 0. Under this scenario, the value of bins[x] afterwards is 2, exactly what one would expect. That is, both threads successfully incremented bins[x]. The element value starts with 0 and becomes 2 after the operations complete. In Fig. 9.4(b), the read-modify-write sequences of the two threads overlap. Note that Thread 1 writes the new value into bins[x] at time period 4. When Thread 2 reads bins[x] at time period 3, it still has the value 0. As a result, the new value it calculates and eventually writes to bins[x] is 1 rather than 2. The problem is that Thread 2 read bins[x] too early, before Thread 1 completes its update. The net outcome is that the value of bins[x] afterwards is 1, which is incorrect. The update by Thread 1 is lost. During parallel execution, threads can run in any order relative to each other. In our example, Thread 2 can easily start its update sequence ahead of Thread 1. Fig. 9.5 shows two such scenarios. In Fig. 9.5(a), Thread 2 completes its update before Thread 1 starts its. In Fig. 9.5(b), Thread 1 starts its update before Thread 2 completes its. It should be obvious that the sequences in Fig. 9.5(a) result in correct outcome for bins[x] but those in Fig. 9.5(b) produce incorrect outcome. The fact that the final value of bins[x] varies depending on the relative timing of the operations involved indicates that there is a race condition. We can eliminate such variation by eliminating the possible interleaving of operation sequences of Thread 1 and Thread 2. That is, we would like to allow the timings shown in Figs. 9.4(a)

and 9.5(a) while eliminating the possibilities shown in Figs. 9.4(b) and 9.5(b). This can be accomplished using atomic operations. An atomic operation on a memory location is an operation that performs a readmodify-write sequence on the memory location in such a way that no other readmodify-write sequence to the location can overlap with it. That is, the read, modify, and write parts of the operation form an undividable unit, thus the name atomic operation. In practice, atomic operations are realized with hardware support to lock out other operations to the same location until the current operation is complete. In our example, such support eliminates the possibility depicted in Figs. 9.4(b) and 9.5(b) since the trailing thread cannot start its update sequence until the leading thread completes its. It is important to remember that atomic operations do not enforce particular execution order between threads. In our example, both orders shown in Figs. 9.4(a) and 9.5(a) are allowed by atomic operations. Thread 1 can run either ahead of or behind Thread 2. The rule being enforced is that if both threads perform atomic operations on the same memory location, the atomic operation performed by the trailing thread cannot start until the atomic operation of the leading thread completes. This effectively serializes the atomic operations being performed on a memory location. Atomic operations can be performed in CUDA using C++ atomic objects or atomic reference objects and functions on those objects.1 CUDA extends the C++ atomic library, and these extensions can be accessed by including the relevant library as follows: #include <cuda/atomic> 1 We encourage readers who are not familiar with the concepts of the C++ objects, classes, and names paces to refer to the C++ documentation [1] for a deeper understanding. Broadly, a C++ class defines how to create a reference to an object that consists of a collection of data and a set of method functions that can operate on the data. The class is generic as it is defined as a template. Intuitively, defining a class as a template enables library developers to specify generic objects that can be specialized to meet the needs of user applications in terms of the types of data and the options for the functions in the objects thus created.

With the atomic library included, the first step for performing an atomic operation on an object is to create an atomic reference to that object using the cuda::atomic_ref class.2 An atomic reference enables us to perform atomic operations on the object. The cuda::atomic_ref class is defined in the CUDA C++ library as follows: template <typename T, cuda::thread_scope> class cuda::atomic_ref;

The template for the atomic_ref class takes two parameters that reside between angle brackets (<'' and >’’). The first template parameter T specifies the type of the object. Examples of commonly used types are int, unsigned int, and float. The second template parameter cuda::thread_scope specifies the scope of threads that can synchronize with one another using the method functions defined for the class. Common examples of scopes include within the same thread block, within the same GPU device, and across all GPU devices within the same multi-GPU system. The “cuda::” prefix indicates that atomic_ref is declared in the CUDA namespace. Interested readers are referred to the CUDA programming guide for more details. Using cuda::atomic ensures that all accesses to the object are atomic from its creation. In our case, we use atomic references because we may wish to access the bins in non-atomic ways in other parts of the code.

The first step in performing the update operation atomically is to construct an atomic reference to bins[b] named bins_ref (line 06). Recall that the cuda::atomic_ref class is defined as a template. On line 06, the first template parameter, unsigned int specifies that the atomic operation is to be performed on an unsigned integer object. In this case, the unsigned integer object is one of the elements of the bins array. The second template parameter, cuda::thread_scope_device, is a predefined compiletime constant indicating that the atomic operation needs to allow threads in different thread blocks to synchronize with each other. That is, the increments to the same bins element are serialized, whether these increments are performed by threads within the same block or across different blocks in the same GPU device. As a result, an atomic reference bins_ref is constructed for performing atomic operations on the selected bins[b]. Although the constructor on line 06 appears to be complex, it actually just serves as a means to instruct the CUDA C++ compiler on how to generate code for line 07 and adds little execution cost at run time. Having constructed the atomic reference, we can invoke its method functions to perform atomic operations on the object that it references. The CUDA atomic reference class provides functions that perform different kinds of operations such as: addition, minimum, maximum, and, or, xor, etc. In our histogram kernel, we need to perform an integer increment operation, i.e., fetching the old value, adding 1 to generate the new value, and writing the new value to the bins elements. The method function that performs atomic addition operations is fetch_add, which is defined as a generic method function of the cuda::atomic_ref class in the CUDA C++ library as follows: T fetch_add(T arg, cuda::std::memory_order order)

The fetch_add function takes two parameters. The first parameter arg specifies the value to be added, which is 1 on our case. Note that the value must be of the same type (T) as specified for the first template parameter of the atomic reference class that defines the fetch_add function. This ensures that the value to be added to the object is of the same type as the object itself. On line 07 of Fig. 9.6, the fetch_add function is invoked on an unsigned integer object bins[b]. The compiler will treat the first argument passed, i.e., the constant value 1, as an unsigned integer constant. The second parameter order is a compile-time constant defined in the C++ standard library for specifying the restrictions on how the atomic operation may be reordered with respect to other memory accesses performed by the invoking thread. The compiler or the hardware may reorder the execution of memory accesses to optimize the performance of the code. The order parameter specifies which kind of reordering is allowed based on the intent of the programmer. In our case, there is only one other memory access performed by the invoking thread: the one that reads the image[i] element into local variable b. Since b is used to select the object on which the atomic operation is to be performed, the compiler will not be able to reorder the atomic operation with respect to the memory access. At run time, the use of b to select the object presents instruction-level data dependencies to the hardware scheduler. That is, the atomic operation will naturally be forced to wait for the completion of the memory access that reads the image[i] element. Thus, there is no need to specify any additional restriction to prevent them from being reordered with respect to each other. The compile-time constant cuda::memory_order_relaxed used in line 07 of Fig. 9.6 indicates that there is no further restrictions beyond what is already present at the instruction-level. In Chapter 11, we will encounter a use case where specifying additional restrictions on reordering memory accesses is needed. The fetch_add function is defined to return a value, which is of the same type (T) as the first template parameter. The returned value is the old value of the object before the first parameter value is atomically added to it. This return value is not used on line 07 of Fig. 9.6 because the thread is only tasked to increment the selected bins element. It is not concerned with the old value of the element before the increment operation. In Chapter 12 and Chapter 18, we will see other use cases where the return value of the fetch_add function may be needed.

9.3 Latency and throughput of atomic operations

The atomic operation used in the kernel of Fig. 9.6 ensures the correctness of updates by serializing any simultaneous updates to a location. As we all know, serializing any portion of a massively parallel program can drastically increase the execution time and reduce the execution speed of the program. Therefore, it is important that such serialized operations account for as little execution time as possible. As we learned in Chapter 5, the access latency to data in DRAMs can take hundreds of clock cycles. In Chapter 4, we learned that GPUs use zero-cycle context switching to tolerate such latency. In Chapter 6, we learned that as long as we have many threads whose memory access latencies can overlap with each other, the execution speed is limited by the throughput of the memory system. Thus, it is important that GPUs make full use DRAM bursts, banks, and channels to achieve high memory access throughput. It should be clear to the reader at this point that the key to high memory access throughput is to have many DRAM accesses that are simultaneously in progress. Unfortunately, this strategy breaks down when many atomic operations update the same memory location. In this case, the read-modify-write sequence of a trailing thread cannot start until the read-modify-write sequence of a leading thread is complete. As shown in Fig. 9.7, the execution of atomic operations at the same memory location is such that there can be only one in progress. The duration of each atomic operation is approximately the latency of a memory load (left section of the atomic operation time) plus the latency of a memory store (right section of the atomic operation time). The length of these time sections of each read-modify-write operation, usually hundreds of clock cycles, defines the minimal amount of time that must be dedicated to servicing each atomic operation and limits the throughput, or the rate at which atomic operations can be performed. For example, assume a memory system with 64-bit (8-byte) Double Data Rate DRAM interface per channel, 8 channels, 1 GHz clock frequency, and typical access latency of 200 cycles. The peak access throughput of the memory system is FIGURE 9.7 Throughput of atomic operation is determined by the memory access latency.

8 (bytes/transfer)*2 (transfers per clock per channel)* 1 G (clocks per second) * 8 (Channels) = 128 GB/sec. Assuming each data accessed is 4 bytes, the system has a peak access throughput of 32 G data elements per second. However, when performing atomic operations on a particular memory location, the highest throughput one can achieve is one atomic operation every 400 cycles (200 cycles for the read and 200 cycles for the write). This translates into a throughput of 1/400 atomics/clock * 1 G (clocks/second) = 2.5 M atomics/second. This is dramatically lower than most users expect from a GPU memory system. Furthermore, the long latency of the sequence of atomic operations will likely dominate the kernel execution time and can dramatically lower the execution speed of the kernel. In practice, not all atomic operations will be performed on a single memory location. In our image histogram example, the histogram has 256 bins. If the input pixels are uniformly distributed in brightness, the atomic operations are evenly distributed among the bins elements. This would boost the throughput to 256*2.5 M = 640 M atomic operations per second. In reality, the boost factor tends to be much lower than the number of intervals in the histogram because the pixels tend to have biased distribution in brightness. For example, in Fig. 9.1, we see that pixels in the example image are heavily biased towards the brighter levels. The heavy contention traffic to update these high-brightness bins will likely cause significant reduction to the achievable throughput. One approach to improving the throughput of atomic operations is to reduce the access latency to the heavily contended locations. Cache memories are the primary tool for reducing memory access latency. For this reason, modern GPUs allow atomic operations with device scope to be performed in the last-level cache, which is shared among all SMs. During an atomic operation, if the updated variable is found in the last-level cache, it is updated in the cache. If it cannot be found in the last level cache, it triggers a cache miss and is brought into the cache where it is updated. Since the variables updated by atomic operations tend to be heavily accessed by many threads, these variables tend to remain in the cache while the threads perform atomic operations on them. Because the access time to the last-level cache is in tens of cycles rather than hundreds of cycles, the throughput of atomic operations is improved by at least an order of magnitude with this approach. This is an important reason why most modern GPUs support atomic operations in the last-level cache.

9.4 Privatization

FIGURE 9.8. Private copies of the histogram reduce contention of atomic operations.

Another approach to improving the throughput of atomic operations is to alleviate the contention by directing the traffic away from the heavily contended locations. This can be achieved with a technique referred to as privatization that is commonly used to address problems in parallel computing with heavy output interference. The idea is to replicate highly contended output data structures into private copies so that each subset of threads can update its private copy. The benefit is that the private copies can be accessed with much less contention and often at much lower latency. These private copies can dramatically increase the throughput for updating the data structures. The downside is that the private copies need to be merged into the final output data structure after the computation completes. One must carefully balance between the level of contention and the merging cost. Therefore, in massively parallel systems, privatization is typically done for subsets of threads rather than individual threads. In our text histogram example, we can create multiple private histograms and designate a subset of threads to update each of them. For example, we can create two private copies and have even-index blocks to update one of them and odd-index blocks to update the other. As another example, we can create four private copies and have blocks with index i update the private copy numbered i mod 4. A common approach is to create a private copy for each thread block. This approach has multiple advantages that we will see later. Regardless of the approach, once the private histograms have been computed, they are merged into the public copy by being added together. This merger is facilitated by the fact that addition is commutative and associative, so the order in which the private copies are added into the public copy does not matter. Fig. 9.8 shows an example of how privatization is applied to the image histogram example from Fig. 9.3. In this example, the threads are organized into thread blocks, where each thread block consists of 8 threads (in practice, thread blocks are much FIGURE 9.9 Histogram kernel with private bins per thread block in global memory.

larger). Each thread block receives a private copy of the histogram that it updates. As shown in the figure, rather than having contention across all the threads that update the same histogram bin, contention will only be experienced between threads in the same block, and across blocks when merging the private copies at the end. Fig. 9.9 presents a simple kernel that creates and associates a private copy of the histogram to every block. Under this scheme, up to 1024 threads (the maximum allowed per block on current hardware) would work on the same private copy of the histogram. In this kernel, the private histograms are in the global memory. These private copies will likely be cached for reduced latency and improved throughput. The kernel in Fig. 9.9 takes an additional parameter bins_pool (line 02) that points to a pool of global memory allocated by the host to hold all the private copies of the histogram, which amounts to gridDim.x*NUM_BINS integers. Each thread adds an offset of blockIdx.x*NUM_BINS to the bins_pool array to find the location of its block’s private bins bins_priv. This offset shifts the position to the private copy for the block to which the thread belongs. The next part of the kernel in Fig. 9.9 (lines 06-12) is similar to the kernel in Fig. 9.6 with two key distinctions. The first distinction is that bins_priv is used instead of bins such that each thread block updates its own private set of bins. In this case, the level of contention is reduced by a factor that is approximately the number of active blocks across all SMs. The effect of reduced contention can result in a significant improvement in the update throughput for the kernel. The second distinction is that the atomic reference has a scope of cuda::thread_ scope_block (line 09), i.e., a block scope instead of a device scope. In other words, the atomic operations invoked with this reference only need to be synchronized with other threads in the same thread block, not the entire device. Depending on thehardware implementation of atomic operations, such narrower scope may be able to achieve shorter latencies and thus higher throughput. This narrower scope is possible because only threads in the same block contend on the bins in the block’s private histogram. At the end of the execution, each thread block will commit the values in its private copy to the public copy pointed to by bins (lines 15-21). The threads in the block first wait for each other to finish updating the private copy (line 13). Next, the threads iterate over the private histogram bins (line 15), each thread being responsible for committing one or more of the private bins. This iterative approach is used to accommodate an arbitrary number of bins that may be larger than the number of threads in the block. During each iteration, each thread reads the value of the private bin it is responsible for and checks if the bin is non-zero (line 16). If so, the thread commits the value by atomically adding it to the public copy (lines 17-19). Note that the addition needs to be performed atomically because threads from multiple blocks can be simultaneously performing the addition on the same location. Since only one thread from each block will be updating any given bins array element during this phase of the kernel execution, the level of contention for each location is modest. One benefit of creating a private copy of the histogram on a per-thread-block basis is that the threads can use __syncthreads() to wait for each other before committing the private copy to the public copy. Another benefit is that, if the number of bins in the histogram is small enough, the private copy of the histogram can be declared in the block’s shared memory. Recall that any reduction in latency directly translates into improved throughput of atomic operations on the same memory location. Hence, the latency for accessing memory can be dramatically reduced by placing bins in the shared memory. Shared memory is private to each SM and has very short access latency (a few cycles). This reduced latency directly translates into dramatic increase in the throughput of atomic operations. In GPUs that support thread block clusters and distributed shared memory, it is also possible to create a private copy of the histogram on a per-cluster basis. In this case, thread blocks in the same cluster can use cluster-level barrier synchronization to wait for each other before committing the private copy to the public copy. They can also place the private copy of the histogram in their distributed shared memory, which allows them to support a larger number of bins. Fig. 9.10 shows a privatized histogram kernel that stores the private copies of the histogram in the shared memory instead of global memory. The key difference from the kernel code in Fig. 9.9 is that the private copy of the histogram is allocated in shared memory in the bins_s array (line 04) and initialized to 0 in parallel by the threads of the block (line 05-07). The barrier synchronization (line 08) ensures that all bins of the private histogram have been properly initialized before any thread starts to update them. The remaining code is identical to Fig. 9.9, except for one distinction. The distinction is that the first atomic operation is performed on the elements of the shared memory array bins_s (line 14) and the private bin value is later read from there (line 20).

9.5 Thread coarsening

We have seen that privatization is effective at reducing the contention of atomic operations, and that storing the privatized histogram in the shared memory reduces the latency of each atomic operation. However, the overhead of privatization is the need to initialize private copies of the histogram and commit these private copies to the public copy. These initialize and commit operations are done once per thread block. Hence, the more thread blocks we use, the larger this overhead is. The overhead is usually worth paying when the thread blocks are executed in parallel. However, if the number of thread blocks launched exceeds the number that can be executed simultaneously by the hardware, the hardware scheduler will serialize these thread blocks. In this case, the privatization overhead is incurred unnecessarily. We can reduce the overhead of privatization via thread coarsening. In other words, we can reduce the number of private copies that need to be initialized and committed to the public copy by reducing the number of blocks and having each thread process multiple input elements. In this section, we look at two strategies for assigning multiple input elements to a thread: contiguous partitioning and interleaved partitioning. Fig. 9.11 shows an example of the contiguous partitioning strategy. The input is partitioned into contiguous segments and each segment is assigned to a thread. Fig. 9.12 shows the histogram kernel with coarsening applied using the contiguous partitioning strategy. The difference from Fig. 9.10 is on lines 10-12. Therefore, each thread accesses a contiguous segment of input elements. Partitioning data into contiguous segments is conceptually simple and intuitive. On a CPU, where parallel execution typically involves a small number of threads, contiguous partitioning is often the best performing strategy since the sequential access pattern by each thread makes good use of cache lines. Since each CPU cache typically supports only a small number of threads, there is little interference in cache usage by different threads. The data in cache lines, once brought in for a thread, can be expected to remain for the subsequent accesses. In contrast, contiguous partitioning on GPUs results in a sub-optimal memory access pattern. As we learned in Chapter 6, the large number of simultaneously active threads in an SM typically causes so much interference in the cache that one cannot expect data to remain in the cache for all the sequential accesses by a single thread. Instead, we need to make sure that threads in a warp access consecutive locations to enable memory coalescing. This observation motivates interleaved partitioning. Fig. 9.13 shows an example of the interleaved partitioning strategy. During the first iteration, the eight threads access pixels 0 through 7. With memory coalescing, the elements will be fetched with the smallest number of memory transactions. During the second iteration, the four threads access characters 8 through 15 in a coalesced manner as well. It should be clear why this is called interleaved partitioning: the partitions to be processed by different threads are interleaved with each other. Obviously, this is a toy example, and in reality, there will be many more threads. There are also more subtle performance considerations. For example, each thread should process four pixels (a 32-bit word) in each iteration to fully utilize the interconnect bandwidth between the caches and the SMs. Fig. 9.14 shows the histogram kernel with coarsening applied using the interleaved partitioning strategy. Thus, all threads jointly process the first blockDim.x elements of the block segment. In the second iteration, when c is 1, all threads add blockDim.x to their indices and jointly process the next section of blockDim.x elements. In general, in iteration c, each thread adds c*blockDim.x to the index of its first element (segment + threadIdx.x) to find the element it should process in that iteration.

Applying thread coarsening to the histogram kernel creates the opportunity for another level of privatization at the level of the thread. Since each thread processes multiple input elements after coarsening, we can create a copy of the histogram that is private to the thread which the thread can update without using atomic operations. When the thread finishes processing all its input elements, it can then commit its thread-level private histogram to the block-level private histogram using atomic operations. One limiting factor for this optimization is the number of bins in the histogram. If the number of bins is very small, then it would be feasible to allocate a copy of the histogram for each thread. The thread may even place this copy in the shared memory or its own registers. However, if the number of bins in the histogram is large, allocating a private copy of the histogram for each thread would be prohibitively expensive.

FIGURE 9.15. Histogram kernel with thread-level privatization.

One workaround is to not store a private copy of every bin, but rather, only the frequently accessed bins. This workaround is possible because some data sets have a large concentration of identical data values in localized areas. For example, in pictures of the sky, there can be large patches of pixels of identical value. Such high concentration of identical values causes heavy contention and reduced throughput of parallel histogram computation. However, it presents a great opportunity for threadlevel privatization. For such data sets, a simple and yet effective optimization is for each thread to aggregate consecutive updates into a single update if they are updating the same element of the histogram. Thread-level privatization reduces the number of atomic operations to the highly contended histogram bins by having each thread to accumulate the count in a threadprivate bin, thus improving the effective throughput of the computation. Fig. 9.15 shows an image histogram kernel where each thread privatizes a single bin of the histogram: the most recently accessed one. The key changes compared to the kernel in Fig. 9.14 are as follows. The first pixel that a thread is responsible for is loaded (line 12) after a boundary check (line 11) and a thread-level private bin bin_r is initialized to 1 (line 13). Next, the coarsening loop starts at c = 1 (line 14) since the first input pixel has already been loaded. Whenever a new pixel is loaded to bNext (line 17), it is compared to the pixel value corresponding to the thread-level private bin (line 18). If they are the same, the thread simply increments the thread-level private bin (line 19). If they are different, the thread uses an atomic operation to add the thread-level private bin’s old value to the block-level private bin (lines 21-23). It then updates the thread-level private bin’s pixel value to the one it just loaded (line 24) and resets the bin’s counter to 1 (line 25). With this scheme, the update is always at least one element behind. In the extreme case where there are no similar pixels found by the thread, all the updates will simply be always one loop iteration behind. For this reason, after a thread has completed processing all input pixels and exited the loop, the thread needs to perform one more atomic operation for the last pixel (lines 29-31). One important observation is that the kernel with thread-level privatization requires more statements and variables. Thus, if the similarity between consecutive pixel values is low, the kernel may execute at slower speed than the previous kernel. However, if the data distribution exhibits high repetitiveness, thread-level privatization may result in significantly higher speed. The added if-statement can potentially exhibit control divergence. However, if there is either no similarity or heavy similarity, there will be little control divergence since the threads would be all either incrementing the private bin or performing the atomic operation. In the case where control divergence does occur, the control divergence is likely compensated by the reduced contention.

9.7 Summary

Computing histograms is important for analyzing large data sets. It also represents an important class of parallel computation patterns where the output location of each thread is data-dependent, which makes it infeasible to apply owner-computes rule. It is therefore a natural vehicle for introducing the concept of read-modify-write race conditions, and the practical use of atomic operations that ensure the integrity of concurrent read-modify-write operations to the same memory location. Unfortunately, as we explained in this chapter, atomic operations have much lower throughput than simpler memory read or write operations because their throughput is approximately the inverse of two times the memory latency. Thus, in the presence of heavy contention, histogram computation can have surprisingly low computation throughput. Privatization is introduced as an important optimization technique that systematically reduces contention and can further enable the use of shared memory which supports low latency and thus high throughput. In fact, supporting fast atomic operations among threads in a block is an important use case of the shared memory. Thread coarsening is also applied to reduce the number of private copies that need to be merged, and different coarsening strategies that use contiguous partitioning and interleaved partitioning were compared. Finally, thread-level privatization can also lead to further reduction in contention of atomic operations, especially for data sets with high similarity between different data elements.
