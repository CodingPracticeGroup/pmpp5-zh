Chapter 7 Convolution

In the next several chapters, we discuss a set of important patterns of parallel computation. These patterns are the basis of a wide range of parallel algorithms that appear in many parallel applications. We start with convolution, which is a popular array operation that is used in various forms in signal processing, digital recording, image processing, video processing, and computer vision. In these application areas, convolution is often performed as a filter that transforms signals and pixels into more desirable values. Our image blur kernel is such a filter that smooths out the signal values so that one can see the big-picture trend. For another example, Gaussian filters are convolution filters that can be used to sharpen boundaries and edges of objects in images.

Convolution typically performs a significant number of arithmetic operations to generate each output element. For large data sets, such as high-definition images and videos where there are many output elements (pixels), the amount of computation can be huge. On one hand, the output data elements of the convolution computation can be calculated independently of each other, a desirable trait for parallel computing. On the other hand, there is a substantial amount of input data sharing when processing different output data elements with somewhat challenging boundary conditions. These properties make convolution an important use case for sophisticated tiling methods and input data staging methods, which are the focus of this chapter.

Since there is an unfortunate name conflict between the CUDA kernel functions and convolution kernels, we will simply refer to these filter arrays as convolution filters to avoid confusion. Convolution can be performed on input data of different dimensionality: 1D (e.g., audio), 2D (e.g., photo), 3D (e.g., video), etc. In audio digital signal processing, the input 1D array elements are sampled signal volume over time. That is, the input data element xi is the i th sample of the audio signal volume. A convolution on 1D data, referred to as 1D convolution, is mathematically defined as a function that takes an input data array of n elements [x0 , x1 , …, xn−1 ] and a filter array of 2r + 1 elements [f0 , f1 , …, f2r ] and returns an output data array y such that: yi = r ∑ fj +r × xi+j (j =−r)

Since the size of the filter is an odd number (2r + 1), the weighted sum calculation is symmetric around the element being calculated. That is, the weighted sum involves r input elements on each side of the position being calculated, which is the reason why r is referred to as the radius of the filter. Fig. 7.1 shows a 1D convolution example where a 5-element (r = 2) convolution filter f is applied to a 7-element input array x. We will follow the C++ language convention where x and y elements are indexed from 0 to 6 and f elements are indexed from 0 to 4. Since the filter radius is two, each output element is calculated as the weighted sum of the corresponding input element, two elements on the left, and two elements on the right. For example, the value of y[2] is generated as the weighted sum of x[0] (i.e., x[2 + (−2)]) through x[4] (i.e., x[2 + 2]). In this example, we arbitrarily assume that the values of the x elements are [8, 2, 5, 4, 1, 7, 3]. The f elements define the weights, whose values are [1, 3, 5, 3, 1] in this example. Each f element is multiplied to the corresponding x element values before the products are summed together. 7.2 Parallel convolution – a basic kernel

The fact that the calculation of all output elements can be done in parallel in convolution makes convolution an ideal use case for data parallel computing. Based on our experience in matrix multiplication, we can quickly write a simple parallel convolution kernel. Since convolution is often applied to large images, we expect that the effect of control divergence to be from modest to insignificant. A more important performance consideration is the memory bandwidth.

7.3 Memory bandwidth considerations

Following the same approach introduced in Chapter 5 in the context of matrix multiplication, let us analyze the arithmetic intensity of convolution and reason about its demand for memory bandwidth. For simplicity, let us assume that the input array is square and has dimensions n × n. Let us also assume that the filter is square and has dimensions m × m (m = 2r + 1 where r is the filter radius). All array and filter elements are 32-bit (4 B) single-precision floating point values. Let us first calculate the number of arithmetic operations performed by convolution. For each of the n × n output elements, the convolution operation iterates through the m × m filter and performs two arithmetic operations for each filter element, a multiply and an add. Hence, the total number of arithmetic operations performed by the convolution operation is 2 · n2 · m2 FLOP. Now, let us calculate the amount of memory data that the convolution operation needs to access. At a minimum, the operation needs to load the convolution filter and the input array, and needs to store the output array. The filter consists of m2 elements. The input and output arrays consist of n2 elements each. Since each element is 4 B, the total number of bytes that convolution needs to access is 8 · n2 + 4 · m2 . Since the filter is typically much smaller than the array (m « n), we can ignore the accesses to the filter and approximate the number of bytes accessed as 8 · n2 B. Taking the ratio of the number of arithmetic operations performed to the number 2 2 of bytes accessed, we find the arithmetic intensity of convolution to be 2·n8·n·m = 4 · m FLOP/B. In other words, a perfect implementation of convolution that accesses each input and output element only once performs 14 · m2 floating point operations for every byte it accesses in memory. An interesting observation is that the arithmetic intensity of convolution is dependent on the convolution filter size m. Convolutions with small filter sizes have low arithmetic intensity, which makes them memory bound. For example, a convolution with a 3 × 3 filter has an arithmetic intensity of 14 · 32 = 2.25 FLOP/B, which makes it memory-bound on an H100 GPU. It is impossible for this computation to reach the peak compute throughput of the GPU because its performance is limited by the memory bandwidth. On the other hand, convolutions with large filter sizes have a high arithmetic intensity, which makes them compute-bound. For example, a convolution with an 11 × 11 filter has an arithmetic intensity of 14 · 112 = 30.25 FLOP/B, which makes it compute-bound on an H100 GPU. The performance of this computation can come close to the peak compute throughput of the GPU provided that the right optimizations are applied. Let us now turn our attention to our basic convolution kernel in Fig. 7.7 of Section 7.2. On line 10 of Fig. 7.7, each thread in each loop iteration loads two elements (8 B) from the global memory and performs two arithmetic operations on them. We ignore the store operation on line 14 because it is negligible in this kernel since it occurs outside the loop nest. Accordingly, the arithmetic intensity of this implementation is (2 FLOP)/(8 B) = 0.25 FLOP/B. Clearly, this arithmetic intensity is very low regardless of the filter size.

In practice, the actual arithmetic intensity of the kernel is higher because of onchip caching. The same filter and input elements are accessed by multiple threads and are likely to be found in the L1 or L2 caches. Still, to more reliably achieve a higher arithmetic intensity and perform closer to the device’s peak throughput, programmers can use other on-chip memory structures such as shared memory or the constant cache. We discuss constant memory and the constant cache in Section 7.4 and shared memory tiling in Section 7.5.

7.4 Constant memory and caching

There are three interesting aspects of the way the filter array F is used in convolution. First, the size of F is typically small; the radius of most convolution filters is 7 or smaller. Even in 3D convolution, the filter typically contains only less than or equal to 73 = 343 elements. Second, the contents of F do not change throughout the execution of the convolution kernel. Third, all threads access the filter elements. Even better, all threads access the filter elements in the same order, starting from F0,0 and moving by one element a time through the iterations of the doubly nested for-loop in Fig. 7.7. These three aspects make the filter an excellent candidate for constant memory and caching (Fig. 7.8).

FIGURE 7.8. A review of the CUDA memory model.

As we discussed in Chapter 5 (Fig. 5.4), CUDA allows programmers to declare variables to reside in the constant memory. Like global memory variables, constant memory variables are also visible to all thread blocks. The main difference is that the value of a constant memory variable cannot be modified by threads during kernel execution. Furthermore, the size of the constant memory is quite small, currently at 64 KB.

To use constant memory, the host code needs to allocate and copy constant memory variables in a different way than global memory variables. We assume that the radius of the filter is specified in the compile-time constant FILTER_RADIUS. To declare a filter array F in constant memory, the host code declares it as a global variable as follows: #define FILTER_RADIUS 2 constant float F[2*FILTER_RADIUS+1][2*FILTER_RADIUS+1];

This global variable declaration should be outside any function in the source file. The keyword constant (two underscores on each side) tells the compiler that array F should be placed into the device constant memory. Assume that the host code has already allocated and initialized the filter in an array F_h in the host memory with (2 ∗ F I LT ER_RADI U S + 1)2 elements. The contents of F_h can be transferred from the host memory to F in the device constant memory as follows: cudaMemcpyToSymbol(F, F_h, (2*FILTER_RADIUS + 1)*(2*FILTER_RADIUS + 1) *sizeof(float));

The cudaMemcpyToSymbol() API function is a special memory copy function that informs the CUDA runtime that the data being copied into the constant memory will not be changed during kernel execution. In general, the use of cudaMemcpyToSymbol() function is as follows: cudaMemcpyToSymbol(dest, src, size)

where dest is a pointer to the destination location in the constant memory, src is a pointer to the source data in the host memory, and size is the number of bytes to be copied.2 Kernel functions access constant memory variables as global variables. Thus, their pointers do not need to be passed to the kernel as arguments. We can revise our kernel to use the constant memory as shown in Fig. 7.9. Like global memory variables, constant memory variables are also located in DRAM. However, because the CUDA runtime knows that constant memory variables are not modified during kernel execution, it directs the hardware to aggressively cache the constant memory variables during kernel execution. As we discussed in Chapter 5 and Chapter 6, the long latency and limited bandwidth of DRAM form a bottleneck in virtually all modern processors. To mitigate the effect of this memory bottleneck, modern processors commonly employ on-chip cache memories, or caches, to reduce the number of variables that need to be accessed from the main memory (DRAM), as shown in Fig. 7.10. Unlike the CUDA shared memory, or scratchpad memories in general, caches are “transparent’’ to programs. That is, to use CUDA shared memory to hold the value of a global variable, a program needs to declare variables as shared and explicitly copy the value of the global memory variable into the shared memory variable. On the other hand, when using caches, the program simply accesses the original global memory variables. The processor hardware automatically retains the most recently or frequently used variables in the cache and remembers their original global memoryaddress. When one of the retained variables is used later, the hardware detects from their addresses that a copy of the variable is available in cache. The value of the variable is then served from the cache, eliminating the need to access DRAM. There is a tradeoff between the size of a memory and the speed of a memory. As a result, modern processors often employ multiple levels of caches. The numbering convention for these cache levels reflects the distance to the processor. The lowest level, Level 1 or L1, is the cache that is directly attached to a processor core, as shown in Fig. 7.10. It runs at a speed close to the processor in both latency and bandwidth. However, an L1 cache is small, typically up to 128 KB in capacity. L2 caches are larger, in the range of a few hundred KBs to a few tens of MBs, but can take tens to hundreds of cycles to access. They are typically shared among multiple CPU cores, or SMs in a CUDA device, so the access bandwidth is shared among SMs. In some high-end processors today, there are even L3 caches that can be of hundreds of MBs in size. Constant memory variables play an interesting role in designing and using memories in massively parallel processors. Since these constant memory variables are not modified during kernel execution, there is no need to support writes by threads when caching them in an SM. Supporting high-thought writes into a general cache requires sophisticated hardware logic and is costly in terms of chip area and power consumption. Without the need for supporting writes, a specialized cache for constant memory variables can be designed in a highly efficient manner in terms of chip area and power consumption. Furthermore, since the constant memory is quite small (64 KB), a small and specialized cache can be highly effective in capturing the heavily used constant memory variables for each kernel. This specialized cache is called a constant cache in modern GPUs. When all threads in a warp access the same constant memory variable, as is the case of F in Fig. 7.9 where the indices for accessing F are independent of the thread indices, the constant caches can provide a tremendous amount of bandwidth to satisfy the data needs of these threads. Also, since the size of F is typically small, we can assume that all F elements are effectively always accessed from the constant cache. Therefore, we can simply assume that no DRAM bandwidth is spent on accesses to the F elements. With this consideration in mind, let us calculate the arithmetic intensity of the kernel in Fig. 7.9. On line 10 of Fig. 7.9, each thread in each loop iteration loads one element (4 B) from the global memory and performs two arithmetic operations on them. The load from F in constant memory is not counted since it almost always hits the constant cache. We ignore the store operation on line 14 because it is negligible in this kernel since it occurs outside the loop nest. Accordingly, the arithmetic intensity of this implementation is (2 FLOP)/(4 B) = 0.5 FLOP/B. In other words, it is double that of the basic kernel in Fig. 7.7. In practice, the actual arithmetic intensity of the kernel in Fig. 7.9 is even higher because the elements of N are accessed by multiple threads and will sometimes be found in the L1 or L2 cache. Still, we can more reliably optimize the accesses to N using shared memory tiling, as we show in Section 7.5.

There is another way to place the filter weights in constant memory without declaring a global array variable. The CUDA compiler actually places kernel parameters in the constant memory as well. Hence, if the filter weights were passed as kernel parameters, they would also be placed in constant memory. A concise way of passing the filter weights as kernel parameters is to place them in a C++ structure and pass the structure by value. This method would allow the kernel to be called many times with different filter weights without the need to explicitly copy these weights every time using cudaMemcpyToSymbol. The CUDA runtime will still need to copy them as part of the kernel launch process, but the copy operation is done transparently to the programmer. There is yet another way to leverage the constant nature of the filter weights to avoid accessing them from the global memory. If the filter weights do not change across program executions and were known at compile time, their values could be hard-coded in the code itself. However, this approach would make the kernel not reusable for other filter weight values.

7.5 Tiled convolution with halo cells

We can address the memory bandwidth bottleneck of convolution by applying the shared memory tiling optimization. Recall from Chapter 5 that in shared memory tiling, threads collaborate to load input elements into an on-chip memory for subsequent repeated use of these elements. We start by establishing the definitions of input tiles and output tiles since these definitions are important for understanding the implementation of the optimization. We refer to the collection of output elements processed by each block as an output tile. Recall that Fig. 7.6 shows a toy example of a 16 × 16 2D convolution using 4 × 4 = 16 blocks with 4 × 4 = 16 threads each. In that example, there are 16 output tiles. Keep in mind that we use 16 threads per block to keep the example small. In practice, there should be at least 32 threads, or one warp, per block, and typically more to achieve a good level of occupancy and data reuse. We define an input tile as the collection of input elements that are needed to calculate the elements in an output tile. Fig. 7.11 shows the input tile (the shaded patch on the left side) that corresponds to the output tile (the shaded patch on the right side) processed by block1,1 . Note that the dimensions of the input tile need to be extended by the radius of the filter (2 in this example) in each direction to ensure that it includes all the halo input elements needed for calculating the output elements at the edges of the output tile. This extension can make the input tiles significantly larger than output tiles. In this toy example, each output tile consists of 42 = 16 elements whereas each input tile consists of (4 + 2 + 2)2 = 82 = 64 elements. In this case, the input tiles are or 4× larger than the output tiles. However, this large ratio is because we assume a tiny output tile dimension for ease of visualization in the toy example. In practice, the output tile dimensions would be much larger and the ratio between input tile size and output tile size would be smaller. For example, if the output tile size is 16 × 16 = 256, with the same 5 × 5 filter, the input tile size FIGURE 7.11 Input tile and output tile in 2D convolution.

would be (16 + 2 + 2)2 = 400. In this case, the ratio between the input tile size and the output size is about 1.6. Although this ratio is much less than 4, it shows that the input tile size can still be significantly larger than output tiles even for practical output tile dimensions. In this section, we present one method for applying shared memory tiling to convolution. This method entails having all threads in a block collaboratively loading the entire input tile to the shared memory, then calculating the elements of the output tile by accessing the input elements from the shared memory. This method should sound familiar to the reader: the strategy resembles that of the tiled matrix multiplication implementation discussed in Chapter 5. The main difference is that the tiled matrix multiplication implementation in Chapter 5 assumes that the input tiles are of the same dimension as the output tiles, whereas the convolution input tiles are larger than the output tiles. This difference between input tile size and output tile size complicates the design of tiled convolution kernels. There are two simple thread organizations for addressing the discrepancy between the input tile size and the output tile size. The first one launches thread blocks whose dimension matches that of the input tiles. This simplifies the loading of the input tiles as each thread needs to load just one input element. However, since the block dimension is larger than that of the output tile, some of the threads need to be disabled during the calculation of output elements. The second approach launches blocks whose dimension matches that of the output tiles. On one hand, this second strategy makes the input tile loading more complex as the threads need to iterate to ensure that all input tile elements are loaded. On the other hand, it simplifies the calculation of the output elements since the dimension of the block is the same as the output tile and there is no need to disable any threads during the calculation of output elements. We present a kernel based on the first thread organization and leave the second organization as an exercise to the reader.

FIGURE 7.12. A tiled 2D convolution kernel using constant memory for F.

Fig. 7.12 shows a kernel that is based on the first thread organization. Each thread first calculates the column index (col) and row index (row) of the input/output element that it is responsible for loading/computing (lines 06-07). The kernel allocates a shared memory array N_s whose size is the same as an input tile (line 09) and loads the input tile to the shared memory array (lines 10-15). The conditions on line 10 are used by each thread to check if the input tile element it is attempting to load is a ghost cell. If so, the thread does not perform a memory load. Rather, it places a zero into the shared memory. All threads perform a barrier synchronization (line 15) to ensure that the entire input tile is in place in the shared memory before any thread is allowed to proceed with the calculation of output elements. Now that all the input tile elements are in the N_s array, each thread can calculate its output P element value using the N_s elements. Keep in mind that the output tile is smaller than the input tile and the blocks are of the same size as the input tiles. For this reason, only a subset of the threads in each block are used to calculate the output tile elements. There are multiple ways we can select a subset of the block’s threads to calculate the output tile elements. Our implementation deactivates FILTER_RADIUS exterior layers of threads, as illustrated in Fig. 7.13. In our implementation, we deactivate FILTER_RADIUS = 1 exterior layer of threads. The heavy-line box at the center of the left side encloses the active threads for calculating the output tile elements. In this example, the threadIdx.x and threadIdx.y values of the active threads both range from 1 to 6. Fig. 7.13 also shows the mapping of the active threads to the output tile elements. Active thread (tx, ty) calculates output element (tx – FILTER_RADIUS, ty -FILTER_RADIUS) using a patch of input tile elements whose upper-left corner is element (tx – FILTER_RADIUS, ty – FILTER_RADIUS) of the input tile. Thus, the row and the col variables provide the index of the output element assigned to each active thread. The tiled 2D convolution kernel in Fig. 7.12 is significantly longer and more complex than the basic kernel in Fig. 7.9. We introduced the additional complexity to reduce the number of DRAM accesses for the N elements. The goal is to improve the arithmetic intensity of the kernel so that the achieved performance is not limited or less limited by the memory bandwidth. Recall from Section 7.4 that the arithmetic intensity of the kernel in Fig. 7.9 is 0.5 FLOP/B. Let us now derive the arithmetic intensity for the kernel in Fig. 7.12. For the blocks that handle tiles at the edges of the data, the threads that handle ghost cells do not perform any memory access for these ghost cells. This reduces the number of memory accesses for these blocks. We can calculate the reduced number of memory accesses by enumerating the number of threads that use each ghost cell. However, it should be clear that for large input arrays, the effect of ghost cells for small filter sizes will be insignificant. So, we will ignore the effect of ghost cells when we calculate the arithmetic intensity of tiled convolution kernels, and only consider the internal thread blocks whose halo cells are not ghost cells. We now calculate the arithmetic intensity for the tiled kernel in Fig. 7.12. Let t represent the size of the square output tile along one dimension (i.e., OUT_TILE_DIM) and m represent the filter dimension (i.e., 2*FILTER_RADIUS+1). Every thread assigned to an output tile element performs one multiplication and one addition for every element of the filter. Therefore, the threads in an internal block collectively perform t 2 · m2 · 2 arithmetic operations. As for the global memory accesses, all the global memory loads have been shifted outside the loop nest to the code that loads the input elements into the shared memory. Each thread assigned to an input tile element loads one 4 B input value. Since the input tile dimension (IN_TILE_DIM) is t + m − 1, the total number of bytes that are loaded by each internal block is (t + m − 1)2 · 4. Since the loads are outside the loop nest, they no longer significantly outnumber the stores so we must also consider the stores in our analysis. The threads of an internal thread block collectively store an entire t × t output tile of elements that are 4 B each. Hence, the total number of bytes stored is t 2 · 4. Taking the ratio of the arithmetic operations performed by an internal block to the number of bytes the block loads, we find the arithmetic intensity of the tiled convolution kernel in Fig. 7.12 to be: t 2 · m2 · 2 = · m2 · 1 m−1 ((t + m − 1) + t ) · 4 4 2 · (1 + t ) + 2 It is notable that this arithmetic intensity is closer to the ideal arithmetic intensity of 14 · m2 derived in Section 7.3. It is attenuated by a factor that approaches 1.0 as the output tile dimension t increases. Intuitively, a larger output tile enables us to reuse input tile elements that are loaded to shared memory to compute a larger number of output tile elements. Hence, a larger t provides a higher arithmetic intensity. Of course, t in our kernel implementation is limited by multiple hardware resource constraints such as the thread block size limit and the shared memory capacity limit. We cover optimization techniques to overcome these challenges in Chapter 8.

FIGURE 7.14. Arithmetic intensity as a function of tile size and filter size for 2D tiled convolution.

Fig. 7.14 shows how the value of the expression we derived for the arithmetic intensity of the tiled convolution kernel in Fig. 7.12 varies for different filter sizes and tile dimensions. It is clear that the computation is memory bound for small filter and tile dimensions, and compute bound for large filter and tile dimensions. For our example with a 5 × 5 filter and 28 × 28 output tiles (32 × 32 input tiles), the arithmetic intensity is 5.42 FLOP/B. In practice, it could be larger because some values used by different thread blocks can be found in the caches. This value is reasonably close to the ideal arithmetic intensity with a 5 × 5 filter, which is 6.25 FLOP/B. The tiled convolution kernel implemented in Fig. 7.12 has a number of inefficiencies. Much of the inefficiency has to do with the fact that the input tile dimensions and block dimensions are larger than the output tile dimensions because of the loading of halo cells. The first inefficiency is that the implementation launches threads that only load data from global memory to shared memory, but do not participate in the computation stage, thereby wasting compute resources. While this approach may be beneficial for memory-bound kernels where having more parallelism when accessing memory is useful, it may become a drawback in compute-bound kernels where the resources wasted by the excluded threads are more valuable. The second inefficiency is that the implementation has output tile dimensions that are not powers of two in size, which may cause misaligned memory accesses when storing the final result to the global memory. Since the maximum size of the thread block (and input tile) is 32 × 32, the output tile for a 5 × 5 filter is 28 × 28. Hence, the output tiles stored by each thread block are not perfectly aligned in memory which can cause some inefficiency when storing them. The third inefficiency is that supporting larger filter dimensions requires shrinking the output tile because the size of the input tile cannot be expanded. As we have seen, shrinking the output tile results in reducing the arithmetic intensity of the kernel, not to mention exacerbating the two aforementioned inefficiencies. To overcome these issues, one could match the block size to the output tile dimension and have threads iterate to load the larger input tile to shared memory. This alternative corresponds to the second thread organization mentioned earlier in this section and left as an exercise for the reader. Another possibility is to avoid loading the halo cells to shared memory entirely and rely on the caches for accessing them quickly. 7.6 Tiled convolution using caches for halo cells

Recall that the halo cells of an input tile of a block are also the internal elements of neighboring tiles. For example, in Fig. 7.11, the lightly shaded halo cells of an input tile are also internal elements of the input tiles of neighboring blocks. There is a significant probability that by the time a block needs to its halo cells, they are already in the L2 cache due to the accesses by its neighboring blocks. As a result, the memory accesses to these halo cells may be naturally served from L2 cache without causing additional DRAM traffic. That is, we can leave the accesses to these halo cells in the original N elements rather than loading them into the N_s. Doing so enables us to use the same dimension for the shared memory input tile and the output tile, and only load the internal elements of each input tile into the shared memory.

7.7 Summary

Fig. 7.15 shows a 2D convolution kernel using caching for halo cells. In this tiled kernel, the shared memory N_s array only needs to hold the internal elements of the tile. Thus, the input tiles and output tiles are of the same dimension, which is defined as constant TILE_DIM (line 1). With this simplification, N_s is declared to have TILE_DIM elements in both the x and y dimensions (line 6). Because the input tiles and output tiles are of the same size, the thread blocks can be launched with the same size of the input/output tiles. Loading of the N_s elements becomes simpler since each thread can simply load the input element that has the same row and column index as its assigned output element (lines 4-5, 7-11). The condition for loading an input element is also simplified in line 7 because the kernel no longer loads halo cells into shared memory so there is no danger of loading ghost cells. Thus, the condition only needs to check for the usual boundary condition that a tile may extend beyond the valid range of the input data. The body of the loop that calculates the elements of P, however, becomes more complex. It needs to add conditions to check for use of both halo cells and ghost cells. The handling of halo cells are done with the conditions on lines 17-20, which test if the input element falls within the interior of the input tile. If so, the element is accessed from the shared memory. If not, the conditions on lines 24-27 check if the halo cells are ghost cells. If so, no action is taken for the element since we assume that the ghost values are 0. Otherwise, the element is accessed from the global memory. The reader should verify that the conditions for handling the ghost cells are similar to those used in Fig. 7.7. A subtle advantage of the kernel in Fig. 7.15 compared to the kernel in Fig. 7.12 is that its block size, input tile size, and output tile size can be the same and can be a power of two. Because the input tile size and output tile size are different for the kernel in Fig. 7.12, there is likely more memory divergence and control divergence during the execution of that kernel.

In this chapter, we have studied convolution as an important parallel computation pattern. While convolution is used in many applications such as computer vision and video processing, it also represents a general pattern that forms the basis of many parallel algorithms. For example one can view the stencil algorithms in partial differential equation (PDE) solvers as a special case of convolution, and this will be the subject of Chapter 8. We will also apply much of what we learned in this chapter on convolutional neural networks in Chapter 20. We presented a basic parallel convolution implementation whose performance is limited by DRAM bandwidth for accessing both the input and filter elements. We then introduced constant memory and a simple modification to the kernel and host code to take advantage of constant caching and eliminate practically all DRAM accesses for the filter elements. We further introduced a tiled parallel convolution implementation that reduces DRAM bandwidth consumption by leveraging the shared memory whileintroducing more control flow divergence and programming complexity. Finally, we presented a tiled parallel convolution implementation that takes advantage of the L1 and L2 caches for handling halo cells. We presented an analysis of the benefit of tiling in terms of elevated arithmetic intensity. This analysis is an important skill that was introduced in Chapter 5 and will be useful in understanding the benefit of tiling for other patterns as well. Through the analysis, we learned about the limitation of small filter and tile sizes. Although we have shown examples for only 1D and 2D convolution, the techniques are directly applicable to 3D convolutions as well. In general, the index calculation for the input and output arrays is more complex due to higher dimensionality. Also, one will have more loop nesting for each thread since multiple dimensions need to be traversed when loading tiles and/or calculating output values. We encourage the reader to complete these higher dimension kernels as homework exercises.
