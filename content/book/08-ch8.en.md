The data processed by stencil-based algorithms are discretized quantities of physical significance, such as mass, velocity, force, acceleration, temperature, electrical field, and energy whose relations with each other are governed by differential equations. A common use of stencils is to approximate the derivative values of a function based on the function values within a range of input variable values. Stencils bear strong resemblance to convolution in that they both calculate the new value of an element of a multidimensional array based on the current value of the element at the same position and those in the neighborhood in another multidimensional array. Therefore, stencils also need to deal with halo cells and ghost cells. Unlike convolution, a stencil computation is used to iteratively solve the values of continuous and differentiable functions within the domain of interest. The data elements and the weight coefficients used for the elements in the stencil neighborhood are governed by the differential equations being solved. Some stencil patterns are amenable to optimizations that are not applicable to convolution. In the solvers where initial conditions are iteratively propagated through the domain, the calculations of output values may have dependences and need to be performed according to some ordering constraints. Furthermore, because of the numerical accuracy requirements in solving differential equations, the data processed by stencils tend to be high-precision floating data that consume more on-chip memory for tiling techniques. Due to these differences, stencils tend to motivate different optimizations than convolution. In general, structured grids cover an n-dimensional Euclidean space with identical parallelotopes (e.g., segments in 1D, rectangles in 2D, bricks in 3D). As we will see, with structured grids, derivatives of variables can be conveniently expressed as finite differences. Therefore, structured grids are mainly used in finite-difference methods. Unstructured grids are more complex and are used in finite-element and finite-volume methods. For simplicity, we only use regular grids and thus finite-difference methods in this chapter. In a discrete representation, one needs to use an interpolation technique such as linear or splines to derive the approximate value of the function for x values that do not correspond to any of the grid points. The fidelity of the representation, or how accurate the function values from these approximate interpolation techniques are, depends on the spacing between grid points: the smaller the spacing, the more accurate the approximations. By decreasing the spacing, one can improve the accuracy of the representation at the cost of more storage and, as we will see, more compute when we solve a partial differential equation. The fidelity of a discrete representation also depends on the precision of the numbers used. Since we are approximating continuous functions, floating-point numbers are typically used for the grid point values. Mainstream CPUs and GPUs supportdouble-precision (64-bit), single-precision (32-bit), half-precision (16-bit), and other representations (see Appendix A). Among these, double-precision numbers offer the best precision and the most fidelity in discrete representations. However, modern CPUs and GPUs typically have much higher arithmetic computation throughput for single-precision and half-precision arithmetic. Also, since double precision numbers consist of more bits, reading and writing double precision numbers consumes more memory bandwidth. Storing these double precision numbers also requires more memory capacity. This can pose a significant challenge for tiling techniques that require a significant number of grid point values to be stored in on-chip memory and registers in order to achieve high arithmetic intensity, as we learned in Chapter 7. Let us discuss stencils with a little more formalism. In mathematics, a stencil is a geometric pattern of weights applied at each point of a structured grid. The pattern specifies how the values of the grid point of interest can be derived from the values at neighboring points using a numerical approximation routine. For example, a stencil may specify how the derivative value of a function at a point of interest is approximated using finite differences between the values of the function at the point and its neighbors. Since partial differential equations express the relations between functions, variables, and their derivatives, stencils offer a convenient basis for specifying how finite difference methods numerically compute the solutions to partial differential equations. For example, assume that we have a function f (x) discretized into a 1D grid array F and we would like to calculate the discretized derivative of f (x), f ′ (x). We can use the classic finite difference approximation for the first derivative: f ′ (x) = f (x + h) − f (x − h) + O(h2 ) 2h That is, the derivative of a function at point x can be approximated with the difference of the function values at the two neighboring points divided by the difference of the x values of these neighboring points. The value h is the spacing between neighboring points in the grid. The error is expressed by the term O(h2 ), meaning that the error is proportional to the square of h. Obviously, the smaller the h value, the better the approximation. In our example in Fig. 8.1, the h value is π6 or 0.52. The value is not small enough to make the approximation error negligible but should result in a reasonably close approximation. Since the grid spacing is h, the current estimated f (x − h), f (x), f (x + h) values are in F [i − 1], F [i], and F [i + 1] where x = i · h. So, we can calculate the derivative values of f (x) at each grid point into an output array FD: F D[i] = F [i + 1] − F [i − 1] 2·h for all the grid points. ## Memory bandwidth considerations {#sec-8-3}

Let us assume that the size of the grid is n × n × n. Since we only perform a stencil computation for the internal points in the grid, the total number of grid point values we compute is (n − 2)3 . To compute each of these values, we must perform 13 floating-point operations (seven multiplications and six additions). Overall, the total number of arithmetic operations performed is 13 · (n − 2)3 FLOP. The data that needs to be accessed to perform these computations are the values of the input grid to be loaded and the values of the output grid to be stored. For the input grid, all the points in the grid except the points in the edges and corners of the 3D space are accessed, which total n3 − 12 · n + 16 values. For the output grid, all the internal grid points are accessed, which total (n − 2)3 values. Each value is a singleprecision floating point number (4 B). Therefore, the total number of bytes accessed is 4 · (n3 − 12 · n + 16 + (n − 2)3 ). Overall, the arithmetic intensity of an ideal 3D 7-point stencil computation, where 13·(n−2)3 each input grid point is loaded only once, is 4·(n3 −12·n+16+(n−2) 3 ) . For a very largevalue of n, this ratio approaches 13 8 = 1.625 FLOP/B. Clearly, this ratio is very small, which makes the 3D 7-point stencil computation memory-bound on modern GPUs. Let us now calculate the arithmetic intensity for the basic stencil sweep kernel in Fig. 8.6. Each thread in the kernel computes one output element, performing 13 floating-point operations (seven multiplications and six additions), loading seven 4 B input values, and storing one 4 B output value. Therefore, the arithmetic intensity for this kernel is (7+1)·4 = 0.41 FLOP/B. This value is significantly lower than the ideal intensity of 1.625 FLOP/B. In practice, if we measure the arithmetic intensity of the kernel, it may be somewhat higher because the elements may be found in the L1 or L2 cache. Still, we can more reliably improve the arithmetic intensity of the kernel by applying optimizations to improve its memory bandwidth utilization. In Section 8.4, we apply shared memory tiling like we did in Chapter 7 to elevate the arithmetic intensity of the stencil kernel.

The kernel is adapted from the basic stencil sweep kernel in Fig. 8.6 so we will only focus on the changes made during the adaptation. Like the tiled convolution kernel, the tiled stencil sweep kernel first calculates the x, y, and z coordinates of the grid point value that each thread is responsible for loading and possibly computing with. The value 1 is subtracted in each expression because the kernel assumes a 3D 7-point stencil with one grid point on each side (lines 02-04). In general, the value subtracted should be the order of the stencil. The kernel allocates an in_s array in shared memory to hold the input tile for each block (line 05). Every thread loads one input element. Like the tiled convolution kernel, each thread loads the beginning element of the cubic input patch that contains the stencil grid point pattern. Because of the subtraction in lines 02-04, it is possible that some of the threads may attempt to load ghost cells of the grid. The conditions i >= 0, j >= 0, and k >= 0 (line 06) guard against these out-of-bound accesses. Because the blocks are larger than the output tiles, it is also possible that some of the threads at the end of the x, y, and z dimensions of a block attempt to access the ghost cells outside the upper bound of each dimension of the grid array. The conditions i < N, j < N, and k < N (line 6) guard against these out-of-bound accesses. All threads in the thread block collaboratively load the input tile into the shared memory (line 07) and use the barrier synchronization to wait until all input tile grid points are in the shared memory (line 09). Each block calculates its output tile on lines 10-21. The conditions on line 10 reflect the simplifying assumption that the boundary points of both the input grid and the output hold initial condition values and do not need to be calculated from iteration to iteration by the kernel. Therefore, threads whose output grid points fall on these boundary positions are turned off. Note that the boundary grid points form a layer at the surface of the grid. The conditions in lines 11-12 turn off the extra threads that were launched just to load the input tile grid points. The conditions allow those threads whose i, j, and k index values fall within the output tile to calculate the output grid points selected by these indices. Finally, each active thread calculates its output grid point value using the input grid points specified by the 7-point stencil while accessing the input values from shared memory instead of global memory. That is, the larger the value of t, the higher the arithmetic intensity. Intuitively, the larger the output tile, the more the input grid point values are reused. The upper bound on the arithmetic intensity as t increases asymptotically is 13 8 = 1.625 FLOP/B, which is the ideal arithmetic intensity derived in Section 8.3. Unfortunately, the 1024 limit on the block size on current hardware makes it difficult to have large t values for the kernel in Fig. 8.8. The practical limit on t is 8 because an 8 × 8 × 8 thread block has a total of 512 threads. Furthermore, the amount of shared memory used for the input tile is proportional to t 3 . Thus, a larger t dramatically increases the consumption of the shared memory. These hardware constraints force us to use small tile sizes for the tiled stencil kernel. There are two major disadvantages to the small limit on the t value imposed by the hardware. The first disadvantage is that it limits the arithmetic intensity. For t = 8, the arithmetic intensity for a 7-point stencil is only 0.96 FLOP/B, which is much less than the ideal arithmetic intensity of 1.625 FLOP/B. The arithmetic intensity decreases as the t value decreases because of the halo overhead. As we discussed in Chapter 7, halo elements are less reused than the non-halo elements. As t decreases, the portion of halo elements in the input tile increases so the arithmetic intensity decreases. For example, for a convolution filter with radius 1, a 32 × 32 2D input tile has 1024 input elements. The corresponding output tile has 30 × 30 = 900 elements, which means that 1024 − 900 = 124 of the input elements are halo elements. The portion of halo elements in the input tile is about 12%. In contrast, for a 3D stencil of order 1, an 8 × 8 × 8 3D input tile has 512 elements. The corresponding output tile has 6 × 6 × 6 = 216 elements, which means that 512 − 216 = 296 of the input elements are halo elements. The portion of halo elements in the input tile is about 58%! The second disadvantage of a small tile size is that it has an adverse impact on memory coalescing. For an 8 × 8 × 8 tile, every warp which consists of 32 threads is responsible for loading 4 different rows of the tile that each have 8 input values. Hence, on the same load instruction, the threads of the warp access at least 4 distant locations in global memory. These accesses cannot be coalesced and underutilize the DRAM bandwidth. This second disadvantage can be overcome by using non-square tiles such that the x-dimension of the thread block is 32 and threads in the same warp access a contiguous chunk of 32 elements. For example, the block dimension could be set to 32, 8, and 4 in the x, y, and z dimensions. Such a block dimension would result in better performance than the cubic blocks with 8 threads in each dimension because it would improve the coalescing of memory accesses. Nevertheless, even with such a rearrangement of the block dimensions, the size of the output tile remains small overall and the arithmetic intensity remains low. This need for a larger tile size to improve arithmetic intensity motivates the approach that we cover in Section 8.5.

Fig. 8.10 shows a kernel with thread coarsening in the z direction for a 3D 7-point stencil sweep. The idea is for the thread block to iterate in the z direction (into thefigure), calculating the values of grid points in one x-y plane of the output tile during each iteration. The kernel first assigns each thread to a grid point in an x-y plane of the output (lines 03-04). Note that i is the z index of the output tile grid point calculated by each thread. During each iteration, all threads in a block process an x-y plane of an output tile and thus they all calculate output grid points whose z indices are identical. Initially, each block needs to load into the shared memory the three input tile planes that contain all the points needed to calculate the values of the output tile plane that is the closest to the reader (marked with threads) in Fig. 8.9. This is done by having all the threads in the block to load the first layer into the shared memory array inPrev_s (lines 08-10) and the second layer into the shared memory array inCurr_s (lines 11-13). For the first layer, inPrev_s is loaded from the front layer of the input tile that has been peeled off for visibility into the internal layers. During the first iteration, all threads in a block collaborate to load the third layer needed for the current output tile layer into the shared memory array inNext_s (lines 15-17). All threads then wait on a barrier (line 18) until everyone has completed loading the input tile layers. The conditions in lines 19-21 serve the same purpose as their counterparts in the shared memory kernel in Fig. 8.8. Each thread then calculates its output grid point value in the current output tile plane using the four x-y neighbors stored in inCurr_s, the z neighbor in inPrev_s, and the z neighbor in inNext_s. All threads in the block then wait at the barrier to ensure that every thread completes its calculation before they move on to the next output tile plane. Once off the barrier, all threads collaborate to move the contents of inCurr_s to inPrev_s and the contents of inNext_s to inCurr_s. This is because the roles played by the input tile planes change when the threads move by one output plane in the z direction. So, by the end of each iteration, the block has two of the three input tile planes needed for calculating the output tile plane of the next iteration. All threads then move into the next iteration and load the third plane of the input tile needed for the output plane of the iteration. The updated mappings of inPrev_s, inCurr_s, and inNext_s in preparation for the calculation of the second output tile plane are illustrated in Fig. 8.11. The advantage of the thread coarsening kernel is that it increases the tile size without increasing the number of threads, and it does not require all planes of the input tile to be present in the shared memory simultaneously. The thread block size is now only t 2 instead of t 3 , where t is the dimension of the input tile, so we can use a much larger t value. For example, we can use t = 32 that would result in a block size of t 2 = 1024 threads. With this t value, the arithmetic intensity of the kernel is 1.52 FLOP/B, which is a significant improvement over the 0.96 FLOP/B intensity of the original shared memory tiling kernel with 8 × 8 × 8 input tiles, and closer to the 1.625 FLOP/B ideal intensity. Moreover, at any point in time, only three layers of the input tile need to be in the shared memory. The shared memory capacity requirement is now 3 · t 2 elements instead of t 3 elements. For t = 32, the shared memory consumption is now at a reasonable level of 3 · 322 · 4 = 12 KB per block.

## Register tiling {#sec-8-6}

Here we present an optimization that can be especially effective for stencil patterns that involve only neighbors along the x, y, and z directions of the center point. All stencils in Fig. 8.3 match this description. The 3D 7-point stencil sweep kernel in Fig. 8.10 reflects this property. Each inPrev_s and inNext_s element is only used by one thread in the calculation of the output tile grid point with the same x-y indices. Only the inCurr_s elements are accessed by multiple threads and truly need to be in the shared memory. The z neighbors in inPrev_s and inNext_s can instead stay in the registers of the single user thread. Keeping data in registers to reduce shared or global memory accesses is called register tiling, as discussed in Chapter 5 and Chapter 6. Fig. 8.12 shows a stencil sweep kernel with register tiling applied to the previous and next planes of the input tile. The kernel is built on the thread coarsening kernel in Fig. 8.10 with some simple but important modifications. We focus our discussion on these modifications. First, we create three register variables inPrev, inCurr, and inNext (lines 05, 07, 08). Register variables inPrev and inNext replace the shared memory arrays inPrev_s and inNext_s, respectively. In comparison, we keep inCurr_s to allow the x-y neighbor grid point values to be shared among threads. Therefore, the amount of shared memory used by this kernel is reduced to one third of that by the kernel in Fig. 8.12. The initial loading of the previous and current input tile planes (lines 09-15) and the loading of the next plane of the input tile before each new iteration (lines 17-19) are all performed with register variables as destinations. Thus, the three planes of the “active part'' of the input tile are held in registers across the threads of the same block. In addition, the kernel always maintains a copy the current plane of the input tile in FIGURE 8.12 Kernel with thread coarsening and register tiling in the z direction for a 3D 7-point stencil sweep.

the shared memory (lines 14 and 34). That is, the x-y neighbors of the active input tile plane are always available to all threads that need to access these neighbors. The kernels in Fig. 8.10 and Fig. 8.12 both keep only the ``active part'' of the input tile in the on-chip memory. The number of planes in the active part depends on the order of the stencil and is 3 for the 3D 7-point stencil. The coarsening and register tiling kernel in Fig. 8.12 has two advantages over the coarsening kernel in Fig. 8.10. First, many reads from and writes to the shared memory are now performed on registers. Since registers have significantly lower latency and higher bandwidth than the shared memory, we expect the code to run faster. Second, each block consumes only one third of the shared memory it did previously. This is, of course, achieved at the cost of three more registers used by each thread, or 3072 more registers per block assuming 32 × 32 blocks. The reader should keep in mind that register use will become even higher for higher order stencils. If the register usage becomes a problem, one can go back to storing some of the planes in shared memory. This scenario represents a common trade-off that often needs to be made between shared memory and register usage. Overall, the data reuse is now spread across registers and the shared memory. The number of global memory accesses has not changed. The overall data reuse if we consider both registers and the shared memory remains the same as the thread coarsening kernel that uses only the shared memory for the input tile. Thus, there is no impact on the consumption of the global memory bandwidth when we add register tiling to thread coarsening.
