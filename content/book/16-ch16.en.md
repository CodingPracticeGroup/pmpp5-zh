Wavefront parallelism is an algorithmic technique for exploiting data parallelism in applications with data dependencies along space and/or time dimensions. In this chapter, we study wavefront parallelism in the context of dynamic programming applications. Dynamic programming represents a class of problems that can be solved by dividing a problem into smaller sub-problems. The solution to the original problem can be found by assembling the solutions found for the sub-problems. Parallelizing dynamic programming algorithms on GPUs entails interesting challenges in terms of hardware utilization and synchronization across threads. In this chapter, we discuss these challenges and present software techniques that address them efficiently.

## Dynamic programming {#sec-16-1}

16.1 Dynamic programming There exist problems, such as all-pair shortest paths in a graph and genomic sequence alignment, whose solutions can be recursively assembled from the solutions to smaller sub-problems. That is, finding optimal solutions to the sub-problems recursively solves the original problem optimally. Dynamic programming is a technique for recursively dividing such problems into smaller sub-problems, deriving and saving the solutions to the sub-problems, and assembling the saved sub-problem solutions into the solution to the original problem. often used multiple times throughout the process, thus reducing redundant computation. Problems that are amenable to dynamic programming exhibit an optimal substructure with overlapping sub-problems. That is, solutions to sub-problems can be assembled to form the solution to the original problem. Dynamic programming methods differ from divide-and-conquer methods in that the solutions to sub-problems in divide-and-conquer methods do not overlap. For example, in the merge sort algorithm (Chapter 14), the sub-problems are disjoint and they can be solved independently. A notable example of dynamic programming is the Fibonacci series, which is generally represented by the following recursive expression: Fi = Fi−1 + Fi−2

(16.1)

If Fi were calculated with simple recursion, the same sub-problems would be solved over and over. For example, solving both Fi and Fi−1 would incur the cost of solving Fi−2 . To avoid such undesirable recomputation, dynamic programming algorithms typically store the solutions to the sub-problems in a table, i.e., memoization or tabulation, depending on the specific implementation approach, as we will discuss in Section 16.2. The stored solutions are reused throughout the process to eliminate redundant computation. The execution of dynamic programming algorithms defines wavefronts, which are groups of intermediate solutions that can be calculated in parallel because there are no dependencies between them. Therefore, parallel execution within each wavefront is a natural way of parallelizing the execution of dynamic programming algorithms. Besides the Fibonacci series, other problems that are commonly solved with dynamic programming algorithms encompass shortest path (e.g., Dijkstra algorithm, Bellman-Ford algorithm, and Floyd-Warshall algorithm), chain matrix multiplication, time series (e.g., dynamic time warping algorithm), Hidden Markov models (e.g., Viterbi algorithm), etc. Bioinformatics is another relevant field where dynamic programming algorithms are of key importance, as they are used to accelerate the solution of problems such as sequence alignment (e.g., Smith-Waterman algorithm, Needleman-Wunsch algorithm), protein folding, RNA structure prediction, and protein-DNA binding [1].

## Implementation approaches {#sec-16-2}

16.2 Implementation approaches There are two main implementation approaches for dynamic programming algorithms: top-down and bottom-up. Code snippets in Fig. 16.1 illustrate both approaches when applied to the Fibonacci series. The top-down approach is based on recursive execution, where each invocation of the function to solve a sub-problem calls the function to solve smaller overlapping sub-problems (i.e., each sub-problem is possibly encountered multiple times when solving a larger sub-problem). The top-down approach employs memoization as a way of holding intermediate results that can later be used to avoid redundant computation when the same sub-problems are encountered later. Each intermediate result is stored in an associative array (e.g., in hash_table in line 11). In the beginning of each invocation (line 4), the recursive function checks if the result it needs to calculate is already in the associative array. If so, it reuses the result from the hash table. Otherwise, it proceeds to either invoke the next recursion (line 7) or return the value (line 10) if the end of recursion has been reached, i.e., when n is either 1 or 0. Although the top-down approach is conceptually simple and matches with the mathematical formulation, it is unfortunately not efficient on GPUs for two main reasons. First, CUDA-enabled GPUs do not efficiently support deep nesting of function calls in kernel code. Device functions are typically inlined by the compiler for efficient execution. Recursive function calls cannot be inlined indefinitely, so they are typically retained as functions calls and cause significant slowdown. Second, accesses to the associative array, i.e., the hash_table, tend to result in uncoalesced memory accesses across threads in the same warp, which could also cause significant slowdown. The bottom-up approach starts by solving the smaller sub-problems and tabulating their solutions, then progressively solving larger sub-problems until the desired problem is solved. The bottom-up approach is iterative, as the for loop in lines 8-10 of the lower code snippet of Fig. 16.1 shows. Each iteration computes a sub-problem, starting from the smallest sub-problems. The solution to every sub-problem is stored in a table (table in line 5). Since the loop iterates from the smaller sub-problems to the larger problems, each iteration is guaranteed to find the solutions of its sub-problems in the table. The set of sub-problems that are solved (also, table cells that are filled) in each iteration is called a wavefront. For the Fibonacci series, wavefront i is composed of a single sub-problem Fi (stored in table cell table[i]). Unfortunately, having only one sub-problem in the wavefront results in sequential execution for this particular problem. Fortunately, many dynamic programming algorithms solve more complex problems where wavefronts consist of multiple sub-problems (often, the tables have multiple dimensions). Sub-problems in the same wavefront can be computed in parallel, since they do not depend on each other. Due to its parallel nature, wavefront parallelism is suitable for GPU computing, but it requires a careful pre-planning of the execution based on a precise understanding of its dynamic behavior (e.g., the wavefront size may grow or shrink) and the dependencies between sub-problems in different wavefronts. We focus on bottom-up approaches for the remainder of this chapter.

16.4 Floyd-Warshall algorithm The Floyd-Warshall algorithm finds the shortest paths between all pairs of vertices of a directed weighted graph.1 To understand how the problem is divided into subproblems, consider the function d(i, j, k), which represents the shortest distance 1 A graph is a data structure that represents relations between entities. For a detailed introduction to graphs, we refer the reader to Chapter 18.

between vertices i and j in a graph using only the vertices from 0 to k as intermediate vertices. Let us assume that we know d(i, j, k − 1) for all i and j , and for some vertex k. In this case, we can find d(i, j, k) using the following recurrence relation: d(i, j, k) = min(d(i, j, k − 1), d(i, k, k − 1) + d(k, j, k − 1)) In other words, it is the shorter distance between going from i to j using only vertices 0 to k − 1 without passing through k, and going from i to k then from k to j . In this way, we have decomposed the problem of finding d(i, j, k) into three smaller subproblems, namely d(i, j, k − 1), d(i, k, k − 1), and d(k, j, k − 1). In the bottom up implementation of the Floyd-Warshall algorithm, we can start from the smallest sub-problems having the smallest value of k and work our way up by increasing k until we have included all vertices in the graph among the intermediate vertices. We already know the values of d(i, j, −1), i.e., the distance between any two vertices i and j using no intermediate vertices. It is simply the weight of the edges between vertices i and j , or infinity if there is no edge. Using the recurrence relation, we can solve d(i, j, 0) for all i and j . We can then solve for d(i, j, 1) for all i and j . We can keep iterating until we have solved d(i, j, N − 1) for all i and j , where N is the number of vertices in the graph. The solution to d(i, j, N − 1) represents the shortest distance between a vertex i and a vertex j using any vertex in the graph as an intermediate vertex, which is the ultimate shortest distance we are looking for. An important observation is that once we have found the solutions of d(i, j, k) for all i and j and for some k, we no longer need the solutions for d(i, j, k − 1) and we can discard them. Hence, although the space of sub-problems defined by d(i, j, k) is O(N 3 ) in size, the space of sub-problem solutions that we need to store at once is only O(N 2 ) in size. For very large graphs, the difference between O(N 2 ) and O(N 3 ) is quite substantial! As the pseudo-code in Fig. 16.3 shows, the algorithm is formulated as three nested for loops with indices k, i, and j. The outer for loop with index k defines the iterations over the sub-problems of different sizes. The order of visiting the vertices k is irrelevant, as long as we visit all vertices k before we exit the loop. The for loops with indices i and j solve the wavefront of sub-problems and update all cells of the dist table. At the beginning of iteration k, the dist table contains the solutions for d(i, j, k − 1) for all i and j . At the end of the iteration, it contains the solutions for d(i, j, k) for all i and j . All table cells can be computed in parallel, which makes Floyd-Warshall suitable for GPU computing. We assume a straightforward bottom-up GPU parallelization of Floyd-Warshall algorithm that assigns one pair of vertices (i, j) per thread. In each iteration k, if the distance from vertex i to vertex k plus the distance from vertex k to vertex j is smaller than the currently observed shortest distance from vertex i to vertex j, a new shortest path from i to j has been discovered and the corresponding thread updates the value of dist[i][j]. At the end of each iteration, threads synchronize via kernel termination and grid relaunch. This global synchronization across all threads of the grid ensures that the possible new distances due to including a vertex k have been calculated and stored in the table dist before the next iteration begins. ## Genome sequence alignment and Smith-Waterman algorithm {#sec-16-5}

16.5 Genome sequence alignment and Smith-Waterman algorithm A genome is the complete set of an organism’s genetic instructions. The DNA is a long string of base pairs (characters): A, C, G, T. For example, the human genome contains 3.2 billion base pairs (bp). Genome analysis helps to understand genetic variations, predict the presence and abundance of microbes, monitor disease outbreaks, develop personalized medicine, etc. For these analyses, the DNA needs to be sequenced (obtained from biological samples). But sequencing machines provide only randomized fragments (reads), which need to be mapped to the reference genome. Depending on the sequencing technology, there are short (50-300 bp) and long reads (10 K-100 K bp). A key step in the read mapping process is sequence alignment, which has been traditionally performed by quadratic-time dynamic programming algorithms such as Smith-Waterman and Needleman-Wunsch. The main data structure of the SmithWaterman algorithm is a dynamic programming table H , called the homology score matrix, or scoring matrix for short. The goal of the alignment is to detect if two sequences are homologous or similar in a biological sense (e.g., they have shared ancestors). Assume that the two sequences being aligned, A and B, have LA and LB base pairs, respectively. The scoring matrix would be a (LA + 1) × (LB + 1) matrix. Within each sequence, we number the base pairs from 1 to the length of the sequence. All cells in row 0 and column 0 of the scoring matrix store the boundary value 0. The 0’s in cells in row 0 indicate no desirable alignment has been found between the nonexistent base pair 0 of B to any of the A base pairs. The 0’s in cells in column 0 indicate no desirable alignment has been found between the non-existent base pair 0 of A to any of the B base pairs. Any other cell of the scoring matrix Hi,j represents the homology score of the alignment between a segment of sequence A (from its first base pair to its i-th base pair) and a segment of sequence B (from its first base pair to its j -th base pair). The higher the homology score, the more similar the two sequence segments are. Note that, as i and j grow, computing Hi,j becomes a sub-problem that can be solved by leveraging previously computed sub-problems, i.e., Hi,j for smaller i and/or j . Thus, the purpose of the scoring table is to store the solutions to previous sub-problems. For any two elements of A and B that we compare individually, we can obtain a similarity score Si,j . The similarity score is positive (e.g., +3), if there is a match (i.e., the two elements Ai and Bj are equal), or negative (e.g., −3), if there is a mismatch (i.e., the two elements Ai and Bj are not equal). When there is a deletion or an insertion, we apply a gap penalty (e.g., 2), which we call deletion_penalty or insertion_penalty, respectively. For the second wavefront, we can calculate H2,1 and H1,2 based on H1,1 as well as boundary cells H0,1 , H0,2 , H1,0 , and H2,0 . For the third wavefront, we can calculate H3,1 , H2,2 , and H1,3 . Each wavefront forms an anti-diagonal of the matrix. One can observe that the size of the wavefront first grows and then shrinks from the first to the last anti-diagonal of the scoring matrix. The entire scoring matrix of the Smith-Waterman algorithm is kept until all wavefronts are calculated. The reason is that the entire matrix is needed for the final traceback process, which starts from the cell with the highest homology score and follows the path of predecessor cells (top, top-left, or left) until reaching a score 0 (in the first row or column). The complete path reconstructs the optimal alignment between the two sequences. The traceback is a sequential process, so in this chapter we focus on the computation of wavefronts, which offers interesting parallelization opportunities.

## Wavefront parallelization: block-level tiling {#sec-16-6}

16.6 Wavefront parallelization: block-level tiling A basic GPU parallelization of the Smith-Waterman algorithm launches one kernel for each anti-diagonal wavefront, and each GPU thread computes one anti-diagonal cell. This approach computes all elements of each wavefront in parallel and guarantees that an entire wavefront is completely computed before the next wavefront starts. Fig. 16.7(a) shows the scoring matrix with dashed diagonal lines over the antidiagonals representing successive kernel launches. We leave the implementation of this basic parallelization as an exercise. This implementation does not exploit data locality across adjacent anti-diagonals, wastes reuse opportunities, and has to pay the cost of launching a new kernel per anti-diagonal. A more efficient parallelization strategy uses block-level tiling, as shown in Fig. 16.7(b). We divide the dynamic programming matrix into tiles and assign each tile to a thread block. Inside a tile, threads compute anti-diagonal entries and synchronize locally (i.e., __syncthreads()) before moving to the next anti-diagonal (dashed diagonal lines). As a result, global synchronization (i.e., kernel termination) is only necessary between ``anti-diagonals of tiles'' (dashed horizontal and vertical lines). An additional advantage of tiling is that we can use the shared memory of each streaming multiprocessor to store the tiles. After a tile is computed, threads can store the tile into global memory in a coalesced manner. Fig. 16.8 shows the host code of a block-level tiling CUDA implementation. We make the simplifying assumption that the input sequences are of the same length (L_seq). Thus, each dimension of the scoring matrix is of length L = L_seq + 1 (line 2), and the scoring matrix is an L × L square matrix (the first row and the first column of the table contain zeros). 16.7 Hyperplane transformation The thread block-level tiling technique in Fig. 16.7(b) improves the performance of wavefront parallelization by reducing kernel calling overhead and leveraging the fast shared memory. However, using square (or rectangular) tiles has two important drawbacks, as Fig. 16.13 illustrates with two adjacent tiles. First, inside a tile, anti-diagonal lengths are non-uniform. As a result, the number of active threads is different for each anti-diagonal, as the left tile in Fig. 16.13 shows.

FIGURE 16.13 Drawbacks of thread block-level tiling with square tiles.

In most iterations, the observed parallelism is lower than the maximum, which implies that many threads remain idle (i.e., warps are underutilized). As a result, for a tile of n × n elements, 2 × n − 1 iterations need to be performed. Second, locality between neighboring tiles that are in two different tile antidiagonals is likely lost because only the last anti-diagonals of a tile are likely to remain in the cache (e.g., L2 in a GPU). In Fig. 16.13, the darkly shaded cells at the top right of the left tile are necessary to compute the initial anti-diagonals of the right tile (lightly shaded cells). However, it is more likely that the moderately shaded cells, which belong to the last anti-diagonals of the left tile, are in the cache since they were computed later, while the darkly shaded cells may have been evicted from the cache. Unfortunately, by the time the moderately shaded cells are used by the corresponding anti-diagonals of the right tile, they will likely have been evicted since these anti-diagonals of the right tile are computed later. To alleviate these two drawbacks, we can transform the square (or rectangular) tiles into hypertiles [2--4]. This is done via an aine transformation, called hyperplane partitioning, which converts rectangular tiles into quadrilaterals. We will limit the transformed tiles to parallelograms that can be formed by shifting the rows of a rectangular tile horizontally so that the cells that correspond to a column in the original tile are aligned with anti-diagonals after the transformation. Such shifting is called shear transformation. For example, in Fig. 16.14, we transform each 3 × 3 square tile in (a) into a 3 × 3 parallelogram hypertile in (b) by shifting its middle row to the left by 1 cell and the bottom row to the left by 2 cells. In these parallelogram hypertiles, each column of the original rectangular tiles is aligned with an anti-diagonal after the transformation. For example, in Fig. 16.14, the three cells from each column of the original tiles in (a) are aligned with an anti-diagonal in the transformed tile in (b). Parallel implementations of the Smith-Waterman algorithm using hypertiles have three advantages over those using rectangular tiles. First, the computation in each tile consists of a sequence of wavefronts of the same length. Thus, each thread block executing the kernel will have the same number of active threads when iterating through these wavefronts, which reduces warp divergence and hardware under-utilization. Fig. 16.14(c) shows that the length of all intra-tile anti-diagonals is fixed, keeping the number of active threads constant. Second, the number of iterations to compute

Third, the last anti-diagonal of one tile passes directly to the first anti-diagonal of the next tile. This increases data locality across thread blocks and can increase cache hits. In Fig. 16.14, assume that a cell with tile-level coordinates (r_tile, q_tile) is mapped to score-matrix-level coordinates (r, q) under square tiling. It takes numTiles_x wavefronts for the square tile approach to reach the top-right corner of the table and another numTiles_x - 1 wavefronts to reach the bottom-right corner of the table. If we think about the thread blocks computing the tiles, each thread block is one tile column ahead of the next thread block. Hence, the thread block that computes the first row of tiles needs numTiles_x iterations to finish, and then we need one more iteration for each of the remaining numTiles_x - 1 rows of tiles. 16.8 More optimizations Synchronization across anti-diagonals of tiles. In the previous sections, we synchronize anti-diagonals of tiles by terminating the kernel and launching a new kernel.

This ensures global synchronization. However, this approach has the disadvantage that each thread block has to wait for all the thread blocks that compute the two previous anti-diagonals, although it only depends on three of these thread blocks. This may cause load imbalance and, thus, entail a potential waste of the computing slots available in the streaming multiprocessors. Recently, CUDA provides cooperative groups, which can synchronize all threads in a warp, a block, several blocks, or an entire grid. Chapter 18 provides a detailed introduction to cooperative groups. An example use of cooperative groups is to allow synchronizing all thread blocks within the grid without relaunching the kernel. For grid-level synchronization, the kernel with cooperative groups needs to use persistent thread blocks. The grid size must be equal to (or less than) the maximum number of concurrent thread blocks that can run on the streaming multiprocessors. The grid-level synchronization provided by cooperative groups can be applied to the computation of tile anti-diagonals in our implementation of the Smith-Waterman algorithm. However, such an implementation would still force each thread block to wait for all thread blocks of the previous two anti-diagonals. A more efficient synchronization mechanism can use an array of flags to signal the completion of tiles. This way, one thread block only needs to check two flags (i.e., the ones corresponding to the tile on top and the tile at the left) and can start computing as soon as they are set. Furthermore, if we use persistent thread blocks and assign one per row of tiles, each thread block will only need to check one flag. Fig. 16.21 illustrates this synchronization mechanism, which resembles the unidirectional synchronization that we covered in Chapter 11 (Scan). The left part of the figure shows an array of flags and the dependencies between tiles. The right part of the figure illustrates the waste of computing slots that the global synchronization may cause, and the potential for saving execution cycles of the inter-block synchronization mechanism. The inter-block synchronization mechanism can also be applied to the hypertiles. In their case, the width of the hypertiles determines the amount of synchronization operations (i.e., checking and updating flags) and the waiting time for a block to start computing a tile. A programmer could tune the width in order to find a performance sweet spot. Small dynamic programming problems. In this chapter, we have used the SmithWaterman algorithm as a running example. Note that we assume that multiple thread blocks are needed for the computation of the scoring matrix. This would be useful for alignment of long sequences (thousands of base pairs). However, for short sequences (hundreds of base pairs), one thread block or even one warp per alignment may be enough to compute the scoring matrix. ## Summary {#sec-16-9}

16.9 Summary Dynamic programming algorithms divide complex problems into simple subproblems recursively. Bottom-up implementations can memoize intermediate results in tables. The dependencies between table cells define wavefronts, which are sets of sub-problems that can be solved in parallel. This chapter has explained how wavefront parallelism can be efficiently exploited on GPUs. Block-level tiling and hypertile transformations provide ways of optimizing the utilization of compute resources. More advanced optimizations that can provide further performance are inter-block synchronization mechanism and the use of DPX instructions.

Our next parallel pattern is sparse matrix computation. In a sparse matrix, the majority of the elements are zeros. Storing and processing these zero elements are wasteful in terms of memory capacity, memory bandwidth, time, and energy. Many important real-world problems involve sparse matrix computation. Due to the importance of these problems, several sparse matrix storage formats and their corresponding processing methods have been developed and are widely used in the field. All these methods employ some type of compaction techniques to avoid storing or processing zero elements at the cost of introducing some level of irregularity into the data representation. Unfortunately, such irregularity can lead to underutilization of memory bandwidth, control flow divergence, and load imbalance in parallel computing. It is therefore important to strike a good balance between compaction and regularization. Some storage formats achieve a high level of compaction at a high level of irregularity. Others achieve a more moderate level of compaction while keeping the representation more regular. The relative performance of a parallel computation using each storage format is known to be heavily dependent on the distribution of non-zero elements in the sparse matrices. Understanding the wealth of work in sparse matrix storage formats and their corresponding parallel algorithms gives a parallel programmer important background for addressing compaction and regularization challenges in solving related problems.
