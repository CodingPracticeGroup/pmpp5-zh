While LLMs were originally developed to process and generate information in text form, multi-modal models (i.e., trained with and used for different types of visual, audio, and other types of data such as scientific data) started to appear. A mechanism, referred to as attention is needed to maintain the context and to identify the parts of the large context that are the most relevant to the generation of the next token. It is therefore important to understand the attention mechanism as well as the Transformer Architecture [1] which is the most popular approach to incorporating attention mechanisms into LLMs.3 20.1 Transformer architecture Most LLMs today employ the transformer architecture and its attention mechanism to capture dependencies between tokens and their relative importance in generating the next token. The attention mechanism resembles a classification process within a neural network. It uses the softmax function to generate probabilities. The probability assigned to each token in the sequence of previous tokens serves as an indication of the relative importance of that token to the generation of the next token. The transformer architecture was originally proposed for transduction tasks, such as machine translation. As such, it was designed with two types of layers. The encoder layers contextualize (or mix) the input tokens by generating a sequence of continuous representations, i.e., floating-point embedding vectors, from a sequence of symbols (e.g., tokens) in the source language. The decoder layers take the sequence of continuous representations from the encoder and generate output tokens (one at a time) in the target language. The decoder does not only take the output of the encoder as input but also the most recent output tokens generated by itself. For this reason, the transformer models are auto-regressive models. Since its first introduction, transformers have been adapted to other types of tasks. Depending on the specific task being performed, a transformer may not need both types of layers. For example, models that perform discriminative tasks such as classification do not need a decoder because they do not generate text in a target language. On the other hand, decoder-only models can perform generative tasks, such as text generation. This is the case of LLMs, where text is generated as a response to a user’s query but not as a sequence-to-sequence transformation. In this section, we focus on the architecture of decoder-only transformers. For more details on the encoder-decoder transformer architecture, we refer the reader to [1]. A sample LLM design based on the decoder-only transformer architecture is shown in Fig. 20.1. We briefly describe its main components as follows. The Tokenizer ➊ converts the text for the input document or query into a sequence of tokens, i.e., integer IDs that represent a character or a short sequence of characters. The mapping of text into tokens is based on the concept that a finite vocabulary can be learned from any given set of training documents in the target language. The collection of unique tokens thus learned and recognized by the tokenizer in an LLM form the vocabulary of the LLM. Each tokenizer has its own definition of tokens and approach to translating text input into tokens. When an LLM is trained, unique IDs are assigned to the tokens as they are encountered in the training document. That is, each time the tokenizer decides to form a token from the next text fragment, it will check if the same text fragment was previously encountered. If not, a new text fragment has been discovered and a new ID number is assigned to this text segment and will be used as the token representation of the text fragment. A mapping from the text fragment to its assigned token ID is recorded for future lookup. If the text fragment was encountered earlier in the training process, the previously assigned token ID is found through the mapping and will be used to represent the text fragment. The mapping from text fragments to token IDs is part of the outcome of training. During inference, each time the tokenizer decides to form a token from a text fragment, the mapping is used to look up the token ID assigned to the text fragment. This token ID becomes the next output of the tokenizer. Strictly speaking, tokens are the text fragments that form the vocabulary of an LLM whereas token IDs are the integer representation of the tokens inside the LLM. When we describe the operations of an LLM, we will use the terms token and token ID interchangeably unless there is a need to be precise. The Embedding layer ➋ implements a function that converts tokens, i.e., token IDs generated by the tokenizer, into embeddings, i.e., their floating-point vector representation. We will use the terms ``embedding'' and ``embedding vector'' interchangeably. This is done via a lookup into an embedding table. The embedding value for each token is also learned from the documents during training. The reason for this conversion is that LLMs are machine learning models that are trained using numerical methods. The training process typically employs gradient-descent approaches that require all functions of the model to be differentiable and all input and parameter values to be in continuous form which is approximated by the floating-point representation. The Positional Encoding layer ➌ adds sequence order information to the input embedding vectors of the input tokens. Positional encoding informs the attention mechanism of the physical position and proximity of tokens in the input, a factor that is considered when determining the relevance of previous input and output tokens to the generation of the next output token. The embeddings of the entire sequence of tokens of the current conversation between the user and the system (user input, system added input, and output) are accumulated into a matrix according to their order of generation. Each row of the matrix is the embeddings of one token. This matrix is the input of the first transformer layer. The Transformer layers ➍ transform the embeddings to extract dependencies among tokens. Each transformer layer contains a multi-head attention sub-layer, an addition and normalization sub-layer, a feed-forward sub-layer, and another addition and normalization sub-layer. The multi-head attention sub-layer ➎ consists of a parallel array of attention heads, each of which performs a linear projection of the embeddings using matrix multiplication. The matrices used in the linear projection are learned in the training process and effectively perform a coordinate transformation on the embedding vectors to make subsequent similarity comparisons more effective. The projections then go through another matrix multiplication that measures the similarity between a token and all the tokens that were generated before it. The outputs from the multiple attention heads are concatenated together and then usually linearly transformed to produce the combined output of the multi-head attention sub-layer. An Addition and Normalization (Add & Norm) sub-layer ➐ follows the multihead attention sub-layer. The addition operator after each feed-forward sub-layer orattention sub-layer enforces a residual connection to help retain information from the original input. The normalization operator stabilizes the process and improves convergence by normalizing the resulting vectors to fit the desired numerical range of input values to the next layer. Its formula takes the mean (μ) and the standard deviation (σ ) of its input embedding vector elements and learned parameters (γ , β). The Feed-forward sub-layer ➏ typically consists of two linear transformations with a ReLU activation in between.4 Intuitively, the attention layers identify similarities/dependencies between tokens and produce new versions of the token embeddings based on similarity-weighted linear combination of token embeddings generated before them. The feed-forward sub-layers add semantic meaning to these new versions of the token embeddings. Another Addition and Normalization sub-layer follows the feed-forward sublayer to help retain the information from the original input to the feed-forward sub-layer and improve convergence while finalizing the output of the transformer layer. The number of transformer layers is referred to as the model depth and varies across LLMs. The attention heads, which perform large-scale matrix multiplications, are the most computationally expensive components of the transformer architecture and will be the focus of the remaining parts of this chapter. The Un-embedding layer ➑ converts the embeddings from the last transformer layer into probability distributions among tokens, which is used to generate the next output token. Model dimensions are critical for generating accurate answers. First, model depth specifies the number of transformer layers in the model. Deeper models provide levels of classifiers and thus can capture more general patterns of dependencies as explained in Appendix B. The second dimension of the model is the number of elements in each embedding vector, called head dimension. Wide embedding vectors, i.e., large head dimensions, capture more semantic information, disambiguate across different concepts, and identify more meaningful dependencies. The third model dimension is the number of heads in each attention sub-layer. These heads capture different types of dependencies between tokens. The size of the model in terms of the number of parameters is the product of the three model dimensions and can be very large, reaching billions or even trillions of parameters (i.e., model weights) in practice. While LLMs require long context for accurate responses, the user inputs are typically too terse and implicit to provide adequate contextual information. As a remedy, the user input is often extended with additional contextual information using a technique called retrieval-augmented generation (RAG). RAG enhances the generation of responses by retrieving relevant documents that provide more specific and up-todate contextual information and concatenate them with the user input to form a much larger, richer context for the LLMs.

During LLM training, the most relevant computation is large-scale matrix-matrix multiplication, which is performed by the attention heads and feed-forward sublayers and can take advantage of the advanced optimization strategies covered in Chapter 15. These matrix multiplications make the attention heads the most computationally expensive computational components of LLM models. We will elaborate on the design of attention heads and the nature of the matrix multiplications that they perform in Section 20.2.

The final step of the attention sub-layer is the matrix multiplication of the N × N probability matrix P and the V matrix. For each token, this matrix multiplication generates a new embedding vector where each element is a similarity/probability weighted sum of the same element of all embeddings in the V matrix. That is, the new embedding vector for each token in the output matrix O is a similarity-weighted sum of the embedding vectors of all previously generated tokens. The output O matrix then goes through the addition-and-normalization and feed-forward sub-layers to become the input matrix X for the next attention sub-layer. Inferencing with an LLM based on the decoder-only architecture in Fig. 20.1 starts with a summarization phase where the system prompt tokens, the user input tokens, and the system-augmented (e.g., RAG) tokens are concatenated to form the X input matrix of the first transformer layer. During the summarization phase, the matrices involved and the computation for each attention head are as shown in Fig. 20.2. The accumulated X matrix is fed to the transformer layers. Each transformer layer generates the input for the next transformer layer. Upon completion of the last transformer layer, the un-embedding layer is used to generate an output token as a text fragment. The next inference iteration starts the autoregression phase, which is also called the decoding phase or the generation phase. The generated output text fragment is fed to the tokenizer, appending the generated embedding vector to the X matrix of the first transformer layer, and activating the transformer layers to generate the next text fragment. Fig. 20.3 illustrates the two phases of LLM inference. During the summarization phase, the initial sequence of the system’s prompt as well as the initial user’s prompt is processed by the tokenizer and embedding layers and accumulated into the X matrix ➊. For simplicity, we omit the systems’ prompt and the typical preamble of the user input in this toy example. As shown in Fig. 20.3, the user wants the LLM to complete the title of this book by entering a prompt ``The title of this book is Programming''. For simplicity, we assume that the LLM in this example uses entire words as tokens. Thus, during the summarization phase, the tokenizer layer, the embedding layer, and the position encoding layer accumulate the embedding vectors for the seven tokens generated from the user input into the X matrix of the first transformer layer. The LLM then invokes the first transformer layer whose completion activates the second transformer layer, etc. When activated, each transformer layer calculates its K, V , Q, QK T , and O before activating the next transformer layer. After all transformer layers and the final un-embedding layer complete their calculation, the LLM produces the first output token (``Massively'' in our example ➋). With the generation of the first output token, the LLM enters the generation phase. During the generation phase, each output token is generated based on the tokens of the initial prompt and the output tokens of all previous iterations. In our example, the token produced at the end of the summarization phase (``Massively'') becomes part of the input to the first iteration of the generation phase, which will produce the next output token. For each new output token, the LLM generates a corresponding new embedding vector (i.e., a new row of matrix X) that will go through the transformer layers ➌. At the end of the first iteration, we obtain a new output token (``Parallel''), which will be the input of the next iteration of the generation phase ➎. The generation phase continues iterating until an end-of-sequence (EOS) token is generated ➏.

For example, element (0, 0) of the product matrix is generated with an inner product between the 0th row of Q and the 0th row of K (i.e., the 0th column of K T ). Note that both of them are the same as the previous iteration so there is no change in the element (0, 0) of the product matrix. In general, the value of any element (r, c) of QK T remains the same as the previous iteration as long as both r and c are less than N since the element is generated from rows of Q and K that remain the same as the previous iteration. The new N th row of QK T is calculated as a vector-matrix multiplication between the (new) N th row of matrix Q and matrix K T . The new N th column of QK T consists of all zero elements because of the zero-masking performed under the causality policy: the tokens generated by the LLM should not be influenced by the token generated after them. The only exception is the N th element of the N th column. This element value is not zero and is covered by the generation of the new N th row.

## Flash attention {#sec-20-5}

a separate softmax kernel, as the one presented in Fig. 20.4, implies global barriers at kernel boundaries as well as several loads/stores of entire matrices from/to the global memory. These global barriers and global memory accesses create a major performance bottleneck that the flash attention formulation [6] alleviates. Flash attention mathematically reformulates the attention heads so that the operations in each attention head can be reordered and fused into a single kernel, and reorganized in a tiled manner. Within the fused kernel, as shown in Fig. 20.8, each thread block takes a horizontal panel (contiguous rows) of Q ➊, the entire K T ➋, and the entire V ➑ to compute their contribution to a horizontal panel of O ➏. The inputs and output for each thread block are shaded gray in Fig. 20.8.

Furthermore, flash attention enables each thread block to iterate through the K T and V matrices in a tiled manner while calculating their contribution to the O tile. These tiles are illustrated in Fig. 20.8 and they are small enough to fit into the onchip memory. In each iteration, each thread block loads a vertical panel (contiguous columns) of K T ➋ and a horizontal panel of V ➑ to compute their contribution to the O tile. All thread blocks execute in parallel, without any global barrier. This iterative approach allows the kernel to keep all intermediate matrices ➌➎ only in the on-chip memory in tiled form and eliminate the global memory traffic for these intermediate matrices. Flash attention is an exact reformulation of the attention mechanism in transformers. It is mathematically identical to the original formulation. flash attention is applicable to training (both forward pass and backward pass) and inference (forward pass). In this chapter, we focus on the forward pass. The backward pass is conceptually simpler because it does not require softmax rescaling, but it requires five matrix multiplications while the forward pass requires only two. The flash attention kernel in Fig. 20.9 applies to the baseline transformer implementation without KV caching. It also applies to the prefill phase of inference with KV caching. For the generation (decode) phase, with KV caching, Q, S, P , and O matrices become vectors Q′ , S ′ , P ′ , and O ′ . Thus, the computations inside a single head change from matrix multiplications to vector-matrix multiplications. To maintain a similar work distribution to that in Fig. 20.8, we can batch multiple requests, i.e., multiple Q_i, into a single matrix. We will discuss batching in the next section. The most recent version of flash attention [9] takes advantage of new capabilities of the Hopper GPU architecture for an additional performance boost. These capabilities are (1) the Tensor Memory Accelerator (TMA), which can asynchronously move tiles from global memory to shared memory for use by the tensor cores without involving compute threads, (2) the tensor core WarpGroup-wide Matrix Multiply Accumulate (WGMMA) instructions, which are asynchronous in contrast to prior architectures, and (3) FP8 precision of the tensor cores. By using warp specialization, this flash attention version achieves better overlap of data movement and computation, and hides softmax execution with asynchronous block-wise GEMMs.

## KV cache arithmetic intensity and memory requirement {#sec-20-6}

. 20.2 illustrates the generation of the K and V matrices during the prefill phase of an LLM inference with KV caching. K and V elements are calculated and cached in memory. Then, during the generation phase (Fig. 20.6), one new row of K and one new row of V are generated for each new token and appended to the KV cache. These K and V rows are generated with vector-matrix operations, which have low arithmetic intensity and underutilize GPU compute resources (see Chapter 5). For this reason, there are a number of optimizations, such as batching and speculative decoding that aim to increase the arithmetic intensity of the generation phase. Batching is a common optimization in all types of DNNs, and has traditionally been used to increase their arithmetic, i.e., computational, intensity. For example, a FIGURE 20.17 Batching in LLM inference.

linear layer with 1024 inputs and 4096 outputs (in 16-bit precision) has a very low arithmetic intensity of 1 floating point operation per byte (FLOPS/B) when the batch size is 1, but its arithmetic intensity increases to 315 FLOPS/B with batch size 512.9 The increased arithmetic intensity is due to the reuse of weights across input vectors. Such a high arithmetic intensity is critical for high GPU utilization. However, LLMs impose a tradeoff between batch size and context length (i.e., KV cache size). In LLM inference, since input queries from multiple users use the same model (e.g., in a chatbot LLM), the weights can be shared among them. This increases the utilization of the GPU in different parts of the computation. For example, the left part of Fig. 20.17 illustrates batching in the fully-connected layers that generate matrices Q, K, and V . Batching increases the arithmetic intensity of the QKV projection by as many times as the batch size. However, note that the KV cache is dependent on the user’s prompt and context. Thus, attention layers do not benefit from batching because they need to maintain and access separate KV caches for different user’s conversations. As a result, batching in LLMs is limited due to the memory requirements of the model weights and the KV cache. Let’s analyze the memory requirements of LLM inference with KV caching and batching. The two main contributors are the model weights (e.g., matrices WQ, WK , and WV ) and the KV cache. The memory size of the model weights depends on the number of parameters of the model (typically, an order of magnitude of several 9 This is the theoretical increase of the arithmetic intensity. In practice, it depends on the tile size used for the implementation.

billions). For example, a model with 7 billion parameters loaded in 16-bit format (FP16 or BF16) takes about 14 GB. Interested readers are referred to the literature for details on the memory requirements of model weights (e.g., [10,11]). The size of the KV cache depends on the number of transformer layers (l) and the hidden dimension. Recall that the hidden dimension is defined as the product of number of (attention) query heads (hq ) and the embedding dimension (d). Eq. (20.7) shows the size of the KV cache per token in bytes for multi-head attention (MHA). Note that we multiply by 2 to include both K and V matrices. p is the precision in bytes. KV _cache_size_MH A = 2 × l × hq × d × p (20.7)

To estimate the memory requirements in a real scenario, we need to consider the KV cache size across all tokens of the sequences in a batch. Eq. (20.8) show the total size of the KV cache across a batch of b sequences of a certain length N. T otal_KV _cache_size_MH A = b × N × 2 × l × hq × d × p (20.8)

For example, let us find the total KV cache size in 16-bit precision for 1 sequence of 4096 tokens for different example LLMs. For the PaLM 2 LLM from Google, the total KV cache size is 1 × 4096 × 2 × 64 × 8192 × 2 = 8 GB, where 64 is the number of transformer layers (l) and 8192 is the hidden dimension (hq × d). For the GPT-3 LLM from OpenAI, the total size is 1 × 4096 × 2 × 96 × 12288 × 2 = 18 GB. For the Llama 2 7B LLM from Meta, the total size is 1 × 4096 × 2 × 32 × 4096 × 2 = 2 GB. With such large KV cache sizes, memory requirements for batching multiple queries in LLM inference can easily exceed the memory capacity of a single GPU. As a result, multi-GPU and multi-node systems are commonly necessary for LLM inference. Note that in the previous analysis, we assume that all sequences of a batch are of the same length. However, in reality, since queries from different users are different, the input sequences as well as the generated output sequences will likely have very different lengths across different users. Thus, batching in LLM inference may cause imbalance across thread blocks, which would result in under-utilization of the GPU resources. To avoid this situation, state-of-the-art LLM model serving systems apply inflight batching mechanisms [12], which schedule and execute batches of multiple requests at a time and schedule a new request to a batch with the lowest workload as soon as a previous one is served. As mentioned before, while batching is effective at increasing the arithmetic intensity (AI) of linear projection operations, batching is not effective at increasing the arithmetic intensity of MHA during inference. We can estimate the arithmetic intensity of MHA by approximating the amount of data movement and the number of floating point operations [13]. For one layer and sequence length N (and assuming p = 1), from Eq. (20.7), the KV cache size is 2 × hq × d × N . The amount of data movement for reading Q’ and writing O’ is 2 × hq × d. The number of floating point FIGURE 20.18 Speculative decoding.

operations to compute (Q′ K T )V is 2 × N × hq × d (we ignore softmax in this estimate). Eq. (20.9) shows that the AI of MHA is approximately as low as 1 floating point operation per byte. AIMH A ≈ 2 × N × hq × d N = ≈1 2 × hq × d + 2 × hq × d × N 1+N (20.9)

A different approach to increase the arithmetic intensity of LLM inference is speculative decoding [14]. This is a model service optimization where a tiny model called the draft model, predicts the output tokens of a large model called the target model. The target model verifies the predictions by the draft model. While the target model has much longer latency, it performs verification on batches of tokens produced by the draft model in parallel. Fig. 20.18 shows an example of speculative decoding. In this example, the speculation depth is 3, i.e., the draft model predicts three consecutive output tokens. Then, the target model verifies the three tokens in parallel. In the first iteration of this example, the target model accepts ``Programming'' and ``Massively'' but rejects ``Efficient''. After the verification by the target model, the accepted tokens are incorporated to the input tokens for the second iteration of the draft model, which will predict three new tokens. Speculative decoding is similar to batching, which is why it increases the arithmetic intensity of the linear projection operations. However, it is a special form of batching where all the tokens in the batch have a common initial set of tokens. For this reason, when applying the attention mechanism, the same KV cache data for these common input tokens is loaded and reused to compute all the output tokens. This reuse of KV cache data is what results in the increase in arithmetic intensity. Without speculative decoding, this KV cache data would have been loaded multiple times, once for each output token.

This is a main reason for the large memory requirements of multi-head attention (MHA) that Eq. (20.8) shows. Two approaches have been proposed to reduce the memory requirements while maintaining an acceptable model accuracy: multi-query attention (MQA) and grouped-query attention (GQA). All three of MHA, GQA, and MQA can take advantage of the flash attention tiling approach explained in Section 20.5. The three alternatives entail different tradeoffs in terms of computation, memory requirements, and model accuracy. Although MQA and GQA alleviate the memory requirements of the KV cache, the batch size and the context length can be still constrained by the limited GPU memory capacity. This limitation is worsened by the fact that the memory reserved for KV caches is typically over-provisioned for the largest possible input. As a result, memory tends to be fragmented and wasted. An example attempt to overcome this scenario is the PagedAttention algorithm [12], which is inspired by the traditional paging mechanisms of operating systems. PagedAttention partitions the KV cache into blocks of equal size that are loaded into the GPU memory (from the larger system memory) when they are needed for computation. Another approach to managing the KV cache is Multi-head Latent Attention (MLA) [16], which employs low-rank joint compression of K and V to reduce memory usage drastically. The key idea of MLA is to compress both K and V vectors for each token into a compressed latent vector (Fig. 20.19(d)). This compression is done in all heads and layers so the reduction in the KV caching memory requirement can be very significant, as Eq. (20.14) shows. T otal_KV _cache_size_MLA = b × N × l × d × p (20.14)

The arithmetic intensity (Eq. (20.15)) increases due to sharing a single latent head across a large number of query heads. AIMLA ≈ 2 × N × hq 2 × N × hq × d = ≈ 2 × hq 2 × hq × d + d × N hq + N (20.15)

The projection matrices used in the compression scheme are learned during training. During inference, K and V are generated (decompressed) by multiplying their latent representations by two up-projection matrices before they are used in the attention calculation. As a result, K and V only need to be preserved in their latent, compressed form between iterations in KV caches of all attention heads and decompressed only when a head is active during the generation phase of an LLM inference. A different, orthogonal technique for scaling LLMs is the Mixture of Experts technique (MoE, e.g., Mixtral [17]). MoE is a sparsely activated architecture where a gating mechanism decides what small subset of specialized sub-networks is used for each input. This allows models to be huge in parameter count but have reduced computational needs per token.
