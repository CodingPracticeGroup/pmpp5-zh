The single value could be the sum, the maximum, the minimum, etc. of all the values in the list. The value can also be of various types: integer, single-precision floating point, doubleprecision floating point, half-precision floating point, characters, etc. All these types of reductions share the same computation structure. Like histogram, reduction is an important computation pattern as it generates a summary from a large amount of data. Parallel reduction is an important parallel pattern that requires parallel threads to coordinate with each other to produce correct results. Such coordination must be done carefully to avoid performance bottlenecks commonly found in parallel computing systems. Parallel reduction is therefore a good vehicle for illustrating these performance bottlenecks and introducing techniques for mitigating them.

Reduction can be performed by sequentially going through every element of the array. Fig. 10.1 shows a sequential sum reduction code in C. Reduction can be defined for many other operators. A product reduction can be defined for a floating-point multiplication operator whose identity value is 1.0. A product reduction of a set of floating-point numbers is the product of all these numbers. A minimum (min) reduction can be defined for a minimum comparison operator that returns the smaller value of the two inputs. A maximum (max) reduction can be defined for a maximum (max) comparison operator that returns the larger value of the two inputs. For real numbers, the identity value for the minimum (minimum) operator is +∞ (−∞). A min (max) reduction of a set of floating-point numbers produces the smallest (largest) number in the list. Parallel reduction algorithms have been studied extensively in the literature. Let us focus on the max reduction tree in Fig. 10.3(a). During the first round (time step), four max operations are performed in parallel on the four pairs of the original elements. These four operations produce partial reduction results -- the four larger values from the four pairs of original elements. During the second time step, two max operations are performed in parallel on the two pairs of partial reduction results and produce two partial results that are even closer to the final reduction result. Thesetwo partial results are the largest value of the first four elements and the largest value of the second four elements in the original input. Note that the order of performing the operations is changed from a sequential reduction algorithm to a parallel reduction algorithm. This will be followed by comparing the value of acc (3) with the input value 7 and updating acc with the winner which is 7. However, in the parallel reduction of Fig. 10.3(a), the input value 7 is first compared with the input value 0 before it is compared against the maximum of 3 and 1. Being able to change the order of performing the operations in this way is essential for parallelizing the reduction operation. To be able to reorder the operations, parallel reduction assumes that the order of applying the operator to the input values does not matter. In a max reduction, no matter what the order is for applying the operator to the input values, the outcome will be the same. This property is guaranteed mathematically if the operator is associative. An operator Θ is associative if (aΘb)Θc = aΘ(bΘc). In other words, if an operator is associative, one can insert parentheses at arbitrary positions of an expression involving the operator and the results are all the same. With this equivalence relation, one can convert any order of operator application to any other order while preserving the equivalence of results. For example, integer addition is associative, i.e., (1 + 2) + 3 = 1 + (2 + 3).2 On the other hand, integer subtraction is not associative, i.e., (1 − 2) − 3 ̸= 1 − (2 − 3). One can convert the subtraction operator into addition of the negative form of the second operand to induce associativity. For example, (1 − 2) − 3 can be converted into (1 + (−2)) + (−3) = 1 + ((−2) + (−3)). As for real numbers, real number addition is associative in the mathematical sense, but strictly speaking, floating-point additions are not associative due to potentially different rounding results for different ways of introducing parentheses. Some applications accept floating-point operation results to be the same if they are within a tolerable difference from each other. Such tolerance allows developers and compiler optimizations to treat floating-point addition as an associative operator for practical purposes. The parallel reduction pattern in Fig. 10.3(a) is called a reduction tree because it looks like a tree whose leaves are the original input elements and whose root is the final result. The term reduction tree is not to be confused with tree data structures where the nodes are linked either explicitly with pointers or implicitly with assigned positions. In reduction trees, the edges are conceptual, reflecting information flow from operations performed in one time step to those in the next time step. To compare the speed of sequential and parallel reduction implementations, we introduce the notions of work and span. The work performed by an implementation refers to the number of operations it performs, whereas the span of an algorithm refers to the time it needs to perform those operations assuming it has infinite resources. For example, the vector addition kernel in Chapter 2, which adds two vectors of size N, launches N threads. During execution, each thread performs one operation that involves reading two input vector elements, performing an addition, and writing one output element. Hence, this kernel performs O(N ) work, i.e., a total of N operations are performed across all threads. We refer to the time period for a thread to perform an operation as a step. When multiple threads are involved, a step is defined as a time period in which all or a subset of the threads each execute an operation in parallel. The span of a computation is measured as the number of steps taken by an implementation assuming an unlimited amount of execution resources. There is no distinction between work and span when analyzing sequential algorithms because operations are performed sequentially so the number of steps taken by the algorithm is directly proportional to the amount of work it performs. In comparison, let us analyze the work and the span of the parallel reduction tree algorithm. In Fig. 10.3(a), the parallel reduction tree performs seven operations to reduce eight values: four max operations during the first time step, two during the second, and one during the third. In general, for N input values, a reduction tree performs 12 N operations during the first round, 14 N operations in the second round, and so on. Therefore, the total number of operations performed is defined by the geometric series 12 N + 14 N + 18 N + · · · N1 N = N − 1 operations. In other words, the parallel reduction tree algorithm performs O(N ) work, which is the same as the sequential reduction algorithm. We will see in Chapter 11 that parallel algorithms do not always perform the same amount of work as sequential algorithms, giving rise to the notion of work efficiency. As for span, a parallel reduction tree takes log2 N steps to complete the reduction process for N input value. Since each step performs one operation, the parallel reduction tree has a span of O(log N ). For example, it can reduce N = 1024 input values in just log2 N = 10 steps assuming that there are enough execution resources. During the first step, we need 12 N = 512 execution resources. Note that the number of resources needed diminishes quickly as we progress in time steps. During the final step, we only need to have one execution resource. The level of parallelism at each step is the same as the number of execution units required. It is interesting to calculate the average level of parallelism across all steps. The average parallelism is the total number of operations performed divided by the number of steps, which is (N − 1)/ log2 N. For N = 1024, the average parallelism in the 10 steps is 102.3, while the peak parallelism is 512 (during the first step). Such variation in the level of parallelism and resource consumption across steps makes reduction trees a challenging parallel pattern for parallel computing systems. It is also noteworthy that data written into the global memory by a thread should not be read by other threads without executing a memory fence operation. ## Reducing control divergence {#sec-10-4}

The kernel code in Fig. 10.5 implements the parallel reduction tree in Fig. 10.6 and produces the expected sum reduction result. Unfortunately, its management of active and inactive threads in each iteration results in a high degree of control divergence. For example, as shown in Fig. 10.6, only those threads whose threadIdx.x values are even will execute the addition statement during the second iteration. As we explained in Chapter 4, control divergence can significantly reduce the execution resource utilization efficiency, or the percentage of resources used in generating useful results. In this example, all 32 threads in a warp consume execution resources but only half of them are active, wasting half of the execution resources. The waste of execution resources due to divergence increases over time. During the third iteration, only one fourth of the threads in a warp are active, wasting three quarters of the execution resources. During iteration 6, only one out of the 32 threads in a warp are active, wasting \(frac{31}{32}\) of the execution resources. If the size of the input array is greater than 32, then entire warps will become inactive after the sixth iteration. For example, for input size of 256, 128 threads or 4 warps would be launched. All four warps would have the same divergence pattern as we explained in the previous paragraph for iterations 1 through 6. During the 7th iteration, Warp 1 and Warp 3 would become completely inactive and thus exhibit no control divergence. On the other hand, Warp 0 and Warp 2 would have only one active thread, exhibiting control divergence and wasting \(frac{31}{32}\) of the execution resource. During the 8th iteration, only Warp 0 would be active, exhibiting control divergence and wasting \(frac{31}{32}\) of the execution resource. In general, the execution resource utilization efficiency for an input array of size N can be calculated as the ratio of the total number of active threads to the total number of execution resources consumed. The total number of execution resources consumed is proportional to the total number of active warps across all iterations since every active warp, no matter how few of its threads are active, consumes full execution resources. This number can be calculated as follows: (N/64 ∗ 6 + N/64 ∗ 12 + N/64 ∗ 14 + · · · + 1) ∗ 32 Here, N/64 is the total number of warps launched since N/2 threads will be launched and every 32 threads form a warp. The N/64 term is multiplied by 6 because all launched warps are active for 6 iterations. After the sixth iteration, the number of warps is reduced by half in each successive iteration. The expression in the parenthesis gives the total number of active warps across all the iterations. The second term reflects that each active warp consumes full execution resources for all 32 threads regardless of the number of active threads in these warps. For input array size of 256, the consumed execution resource is (4\*6 + 2 + 1)\*32 = 864. The number of execution results committed by the active threads is the total number of active threads across all iterations: N/64 ∗ (32 + 16 + 8 + 4 + 2 + 1) + N/64 ∗ 12 ∗ 1 + N/64 ∗ 14 ∗ 1 + · · · + 1 The terms in the parenthesis give the active threads in the first six iterations for all N/64 warps. Starting at the 7th iteration, the number of active warps is reduced by half in each iteration and there is only one active thread in each active warp. For input array size of 256, the total number of committed results is 4 ∗ (32 + 16 + 8 + 4 + 2 + 1) + 2 + 1 = 255. This result should be intuitive because the total number of operations needed to reduce 256 values is 255 operations. Putting the previous two results together, we find that the execution resource utilization efficiency for an input array size of 256 is 255/864 = 0.30. This ratio states that the parallel execution resources did not achieve their full potential in speeding up this computation. On average, only about 30% of the resources consumed contributed to the sum reduction result. That is, we are only using 30% of the hardware’s potential to speed up the computation. Based on the analysis, we see that there is wide-spread control divergence across warps and over time. As the reader might have wondered, there is a better way to assign threads to the input array locations to reduce control divergence and improve resource utilization efficiency. The problem with the assignment illustrated in Fig. 10.6 is that the partial sum locations become increasingly distant from each other FIGURE 10.7 A better assignment of threads to input array locations for reduced control divergence.

and thus the active threads that own these locations are also increasingly distant from each other as time progresses. This increasing distance between active threads contributes to the increasing level of inactivity and resource underutilization. There is, indeed, a better assignment strategy that significantly reduces control divergence. The idea is that we should arrange the threads and their owned positions so that they can remain close to each other as time progresses. That is, we would like to have the stride value to decrease, rather than increase, over time. The revised assignment strategy is shown in Fig. 10.7 for an input array of 16 elements. Here, we assign the threads to the first half of the locations. During the first iteration, each thread reaches halfway across the input array and adds an input element to its owned location. In our example, Thread 0 adds input[8] to its owned position input[0], Thread 1 adds input[9] to position input[1], etc. During each subsequent iteration, half of the active threads drop off and all remaining active threads add an input element whose position is the number of active threads away from its owner position. In our example, during iteration 3, there are two remaining active threads: Thread 0 adds input[2] into its owned position input[0] and Thread 1 adds input[3] into its owned position input[1]. ## Reducing memory access divergence {#sec-10-5}

The simple kernel in Fig. 10.5 has another performance issue: memory access divergence. As we explained in Chapter 5, it is important to achieve memory coalescing within each warp. That is, adjacent threads in a warp should access adjacent locations when they access global memory. Unfortunately, as illustrated in Fig. 10.6, adjacent threads do not access adjacent locations. In each iteration, each thread performs two global memory reads and one global memory write. The first read is from its owned location, the second read is from the location that is of stride distance away from itsowned location, and the write is to its owned location. Since the locations owned by adjacent threads are not adjacent locations, the accesses made by adjacent threads will not be fully coalesced. During each iteration, the memory locations collectively accessed by a warp are of one stride distance away from each other. For example, as shown in Fig. 10.6, when all threads in a warp perform their first read during the first iteration, the locations are two elements away from each other. As a result, twice the number of global memory transactions as that for a coalesced access are triggered, and half the data returned will not be used by the threads. The same behavior also occurs for the second read and the write. During the second iteration, every other thread drops out, and the locations collectively accessed by the warp are four elements away from each other. Four times the number of global memory transactions as that for a coalesced access are performed and only one fourth of the data returned will be used by the threads. This pattern continues and the inefficiency of the accesses increases as the stride increases. This will continue until there is only one active thread for each warp that remains to be active. Only in the case when there is one active thread in the warp, the warp will perform one global memory request. Thus, the total number of global memory requests is: (N/64 ∗ 5 ∗ 2 + N/64 ∗ 1 + N/64 ∗ 12 + N/64 ∗ 14 + · · · + 1) ∗ 3 The first term (N/64 ∗ 5 ∗ 2) corresponds to the first five iterations where all N/64 warps have two or more active threads whose divergent memory accesses trigger two global memory requests, and therefore, each warp triggers two global memory requests. The remaining terms account for the final iterations where each warp has only one active thread and triggers only one global memory request, and half of the warps drop out in each subsequent iteration. The multiplication by 3 accounts for the two reads and one write by each active thread during each iteration. In the 256-element example, the total number of global memory requests performed by the kernel is (4 ∗ 5 ∗ 2 + 4 + 2 + 1) ∗ 3 = 141. For the kernel in Fig. 10.8, the adjacent threads in each warp always access adjacent locations in the global memory so the accesses are always coalesced. As a result, each warp only triggers a minimal number of global memory transactions on any read or write and fully utilizes the returned data. As the iterations progress, entire warps drop out so no global memory access would be performed by any thread in these inactive warps. The active warps still perform coalesced accesses, triggering the minimal number of global memory transactions and fully utilizing the returned data. Half of the warps drop out in each iteration until there is only one warp for the final five iterations. The only period of resource under-utilization occurs when the amount of data requested drops below the size of a single global memory transaction. Since DRAM bandwidth is a limited resource, the execution time of the kernel in Fig. 10.7 is likely to be significantly better than that for the simple kernel in Fig. 10.5. In conclusion, the kernel in Fig. 10.7 offers more efficiency in using both execution resources and DRAM bandwidth compared to the kernel in Fig. 10.5. The advantage comes from both reduced control divergence and improved memory coalescing.

CUDA provides multiple warp-level primitives that allow threads in the same warp to share data and synchronize with each other in ways that threads across different warps cannot. ## Reduction for arbitrary length inputs {#sec-10-9}

All the kernels that we have studied so far assume that they will be launched with one thread block. The main reason for this assumption is that __syncthreads() is used as a barrier synchronization among all the active threads. Recall that __syncthreads() can be used only among threads in the same block. This limits the level of parallelism to 1024 threads on current hardware. For large input arrays that contain millions or even billions of elements, we can benefit from launching more threads to further accelerate the reduction process. Since we do not have a good way to perform barrier synchronization among threads in different blocks, we will need to allow threads in different blocks to execute independently. Fig. 10.17 illustrates the concept of multi-block reduction using atomic operations. The idea is to partition the input array into segments so that each segment is of appropriate size for a block. All blocks then independently execute a reduction tree and accumulate their results to the final output using an atomic add operation. Fig. 10.18 shows the kernel implementation for the multi-block reduction, which has only a few changes compared to the kernel in Fig. 10.16. The partitioning is done by assigning a different value to the segment variable according to the thread’s block index (line 03). The size of each segment is 2\*blockDim.x. That is, each block processes 2\*blockDim.x elements. Thus, when we multiply the size of each segment by blockIdx.x of a block, we have the starting location of the segment to be processed by the block. For example, if we have 1024 threads in a block, the segment size would be 2\*1024 = 2048. The starting locations of segments would be 0 for block 0, 2048 (2048 \* 1) for block 1, 4096 (2048 \* 2) for block 2, etc.

A subtle but important aspect of using the atomic operation to accumulate partial sums into the final sum is that the thread blocks can make their contributions in any arbitrary order with respect to each other. This is because atomic operations only enforce mutual exclusion but not ordering. Therefore, the operator for the reduction must be both commutative and associative in order to benefit from the use of atomic operations to generalize to inputs of arbitrary length. As an alternative to using atomic operations to produce a global reduction from the reduction results of segments, one can have the leader threads of thread blocks to write into a partial sum array using their block index. A new kernel can then be launched with one thread block to produce the final output value. Another alternative is to copy the partial sum array to the host memory and use the CPU to complete the reduction. In systems where atomic operations are not available or are too expensive, using a single-block grid or the host to complete the reduction would make sense. These approaches also give the programmer more control over the order in which the partial sums are accumulated.

## Thread coarsening to reduce overhead {#sec-10-10}

The reduction kernels that we have worked with so far all try to maximize parallelism by using as many threads as possible. That is, for a reduction of N elements, N/2 threads are launched. With a thread block size of 1024 threads, the resulting number of thread blocks is N/2048. However, in processors with limited execution resources, the hardware may have only enough resources to execute a portion of the thread blocks in parallel. In this case, the hardware will serialize the surplus thread blocks, executing a new thread block whenever an old one has completed. To parallelize reduction, we have actually paid a heavy price to distribute the work across multiple threads and thread blocks. As we have seen in earlier sections, hardware underutilization increases with each successive stage of the reduction tree because of more threads become idle. The phase where the hardware is underutilized occurs for every thread block we launch. It is an inevitable price to pay if the thread blocks were to actually run in parallel. However, if the hardware were to serialize these thread blocks, we are better off serializing them ourselves in a more efficient manner. As we discussed in Chapter 6, thread granularity coarsening, or thread coarsening for brevity, is a category of optimizations that serializes some of the work into fewer threads to reduce parallelization overhead. We start by showing an implementation of parallel reduction with thread coarsening applied by assigning more elements to each thread block. Therefore, thread coarsening effectively reduces the overhead from hardware underutilization, synchronization, and access to shared memory. Theoretically, we can increase the coarsening factor well beyond two. However, one must keep in mind that as we coarsen threads, less work will be done in parallel. Therefore, increasing the coarsening factor will reduce the amount of data parallelism being exploited by the hardware. If we increase the coarsening factor too much such that we launch fewer thread blocks than the hardware is capable of executing, we will no longer be able to take full advantage of the available parallel hardware execution resources. The best coarsening factor ensures that there are enough thread blocks to fully utilize the hardware, which usually depends on the total size of the input as well as the characteristics of the specific device.

## Summary {#sec-10-11}

The parallel reduction pattern is important as it plays a key role in many data processing applications. Although the sequential code is simple, it should be clear to the reader that several techniques are needed to achieve high performance parallel execution. These techniques include thread index assignment for reduced divergence, using shared memory for reduced global memory accesses, using warp-level primitives for reduced barrier synchronizations and shared memory access, multi-block reduction with atomic operations, and thread coarsening. Reduction is also an important foundation for the prefix-sum pattern that is an important algorithm component for parallelizing many applications and will be the topic for the next chapter. We reiterate that in practice, programmers do not need to implement parallel reduction from scratch because CUDA libraries such as Thrust [1,2] and CUB [3] provide built-in implementations that are highly optimized for GPUs. However, parallel reduction serves as an excellent vehicle for introducing parallelization and optimization techniques that are applicable in many application contexts.
