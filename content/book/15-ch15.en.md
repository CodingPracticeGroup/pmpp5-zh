Matrix multiplication is an important operation in science, engineering, and graphics applications. Due to its high computation complexity, it exhibits a high degree of data reuse and thus significant optimization opportunities. In Chapter 3, we used matrix multiplication as an example of mapping multi-dimensional grids to data. Subsequently, in Chapter 5, we used matrix multiplication as an example of using shared memory tiling to reduce global memory accesses. In this chapter, we will dive more deeply into matrix multiplication and the advanced optimizations for this important computation on the GPU architecture.

## Background {#sec-15-1}

15.1 Background Matrix-matrix multiplication, or matrix multiplication in short, is widely used in mathematical formulations of science and engineering problems. Conceptually, it is more intuitive to start with vector-matrix multiplication, a special case of matrix multiplication, where the first matrix operand has only one row and thus can be viewed as a vector v. By multiplying a vector v with a matrix B to generate a vector u, i.e., u = v × B, one linearly transforms v into u. That is, each element of u is a linear combination of all elements of v. combining all elements of v into element j of u. For example, in graphics applications, one can perform a coordinate rotational transformation by multiplying the 3D vector coordinate of a point in space with a 3 × 3 matrix, along with a vector addition if shifting is needed and/or multiplying all elements with a scaling factor, to derive its coordinate vector according to a new vantage point along with new orientation and scale. To perform the same linear transformation on multiple vectors, one can collect these vectors into a matrix A, where each row is one of the vectors, and perform a matrix multiplication D = A × B. After multiplication, each row of D contains one of the transformed vectors. Going back to the coordinate transformation example, one may need to scale the matrix multiplication result and perhaps add a (scaled) matrix C, where each row of C is a vector to be added to the corresponding transformed row vector of A. Thus, we have a general form D = αA × B + βC, which is referred to as General Matrix Multiply (GEMM) in linear algebra and high-performance computing communities. It should be clear that the matrix multiplication step A × B is likely the most compute intensive step of GEMM. Thus, we focus on the matrix multiplication step of GEMM in this chapter. Depending on the context of the computation, the matrices involved in the matrix multiplication operation may each be stored in row major or column major order. The particular storage format may be a result of operating on the original matrix or its transpose, as discussed in Chapter 6. Throughout this chapter, we assume that the two matrices involved in the matrix multiplication are both in row major order. However, the optimization techniques we describe can also be applied to other combinations of storage formats. In fact, libraries that support GEMM operations typically support these different combinations. The applicability and benefit of optimizations for matrix multiplication depend on the dimensions of the matrices involved. Before the rise of deep learning, matrix multiplications in applications typically involve matrices of modest dimensions. This is because these applications typically apply linear transformations to vectors with modest numbers of elements. As we will see in Chapter 19 and Chapter 20, one can formulate the training of Convolutional Layers of the Convolutional Neural Networks and the Attention Layers of Large Language Models into multiplications using large matrices. These large-scale matrix multiplications motivate optimizations that were less profitable when applied to smaller-scale multiplications. Many optimizations covered in this chapter are designed to benefit large-scale matrix multiplications.

## Data reuse analysis {#sec-15-2}

15.2 Data reuse analysis Fig. 15.1 reviews tiled matrix multiplication which was covered in Chapter 5, using more general tile dimensions. The threads in the thread block collaboratively iterate over the input tiles of matrices A and B, loading a m × k tile of matrix A and the corresponding k × n input tile of matrix B from global memory to shared

FIGURE 15.1 Review of tiled matrix multiplication.

memory. For each pair of input tiles, the threads compute the partial contribution of the input tiles to each element in the output tile. The output tile is stored collectively in the registers of the threads in the thread block. When the computation is over, the threads in the thread block write the values of the output tile from their registers to the global memory. In Chapter 5, our data reuse analysis assumed that the input and output tiles were square. Let us now analyze the data reuse achieved by tiled matrix multiplication for non-square tiles. For each pair of input tiles, the threads in the thread block collaboratively compute k multiply and k add operations for each of the m × n output elements, making the total number of floating point operations 2 · m · n · k. At the same time, the threads in the thread block will collaboratively load a m × k tile of A and a k × n tile of B where each element loaded is 4 B, making the total number of bytes loaded 4 · k · (m + n). If we take the ratio of these two numbers, we get an arithmetic intensity of 0.5 · m · n/(m + n) operations per byte. As we saw in Chapter 5, a larger arithmetic intensity would allow the computation to better overcome the memory bandwidth bottleneck and achieve better performance. The ratio 0.5 · m · n/(m + n) can be increased by using larger values of m and n, i.e., using larger output tiles. For example, if m = n = 32, the arithmetic intensity would be 8 FLOP/B, which would keep the kernel memory-bound on an H100 GPU (see Chapter 5). On the other hand, if we increase m = n = 128, then the arithmetic intensity would increase to 32 FLOP/B, which would make the kernel compute-bound on an H100 GPU. The intuition behind why increasing m and n improves the arithmetic intensity of the computation is that larger output tiles allow the same input data to be reused

across more output values. For example, in Fig. 15.1, if we increase n from 32 to 128, we enlarge the output tile by 4× in the horizontal direction. In other words, each thread block would calculate the equivalent of four original output tiles. Calculating these output tiles uses the same input tile of A, as shown on the left part of Fig. 15.1. In the original configuration, the four output tiles were calculated using four different thread blocks, each redundantly loading the same input tile of A. After increasing n by 4×, all four output tiles are calculated by only one thread block and the input tile of A needs to be loaded only once by the thread block. One can further reduce the redundant loading of B input tiles by enlarging the height m. This elimination of redundant loading of A and B input tiles across thread blocks enhances data reuse and thus increases arithmetic intensity. We look at how we can increase the tile sizes for tiled matrix multiplication in Section 15.3.

## Using larger tiles with thread coarsening {#sec-15-3}

15.3 Using larger tiles with thread coarsening Using larger tiles in tiled matrix multiplication would necessitate assigning to each thread in the block multiple elements to compute per output tile and multiple elements to load per input tile. Hence, this optimization can be thought of as a thread coarsening optimization, where the overhead of finer-grain parallelization is the need to load the same input value more times by different thread blocks. This optimization is similar to the thread coarsening optimization applied in Chapter 8 on the stencil computation where thread coarsening was also used to increase the output tile size for increased data reuse and arithmetic intensity. Fig. 15.2 illustrates how tiled matrix multiplication can be performed with large tiles. Each thread block computes an output tile of size bM×bN. We refer to the output tile of a thread block as a block-level output tile. When the size of the block-level output tiles is larger than the number of threads in a block, each thread in the block must be responsible for computing multiple elements of the block-level output tile. For example, if each block-level output tile consists of bM×bN = 128 × 128 elements and each thread block has 16 × 16 threads, each block-level output tile can be divided across threads such that each thread takes an output tile of size tM×tN = 8 × 8. We refer to the tM×tN tile taken by a thread as its thread-level output tile. In general, the input and output matrices for matrix multiplication can be logically divided into a hierarchy of tiles. In our example, we have block-level tiles and threadlevel tiles. Each tile in a tile hierarchy can be assigned to a unit of the thread hierarchy. 15.4 Register tiling of the input tiles So far we have used shared memory tiling to overcome the global memory bandwidth bottleneck by loading reused data once to shared memory and then accessing

FIGURE 15.8 Matrix multiplication with register tiling of input tiles.

it multiple times from shared memory. Indeed, in the example of tiled matrix multiplication, an element in the input tile is loaded by one thread from global memory to shared memory, and then loaded by multiple threads from shared memory to their registers to perform the computation. While accessing data from shared memory is much faster than accessing it from global memory, it is still slower than accessing it from a register. Hence, after applying shared memory tiling, the shared memory access latency becomes a new bottleneck in the computation. To overcome the shared memory access latency bottleneck, we observe from Fig. 15.2 that a thread uses the same input value to compute multiple output elements. In our implementation in Section 15.3, the same input value is loaded from shared memory multiple times by the same thread, once for each output element that it contributes to. That is, although each thread defines its own logical thread-level input tile, each time a thread uses a thread-level input tile element, the thread still loads the element from the block-level tile array in shared memory. We can avoid these redundant accesses to shared memory by applying register tiling to the input tiles. In other words, a thread can load each input element it needs from shared memory only once and place it in a register, then reuse that value from the register to compute all the corresponding output values. Fig. 15.8 illustrates how register tiling can be applied to the input tiles. In this figure, a tile of matrix A has already been loaded into shared memory along with the corresponding tile of matrix B. Each thread iterates over its sections of the shared memory input tiles one strip at a time. The thread loads the pair of strips from the shared memory to its registers. The thread then computes the contributions of the pair of input strips to all its output tile elements before proceeding to load the next pair. Fig. 15.9 shows the revised mm() device function for applying register tiling to the input tiles. ## Coalesced storing of the output tile {#sec-15-5}

15.5 Coalesced storing of the output tile In our implementation so far, each thread has been responsible for a large (e.g. 8×8 in Fig. 15.2) thread-level output tile. Using large thread-level output tiles has the advantage of enabling significant data reuse when shared memory tiling and register tiling are applied. However, the large 8×8 thread-level output tile is problematic when we need to store the output tile from the registers to the global memory. In particular, when each thread iterates through its 8×8 thread-level output tile to store it to global memory, threads in the same warp storing adjacent thread-level output tiles issue stores to memory locations that are eight elements apart. The resulting memory access pattern is not coalesced. Using vector store instructions, as mentioned in Section 15.3, partially alleviates this problem because it allows each thread to store four consecutive elements simultaneously. Still, even with vector stores, the four consecutive elements cover only half the width of the thread’s 8×8 output tile. Threads in the same warp storing adjacent output tiles would issue vector store instructions that are four elements apart. The resulting memory access pattern is still not completely coalesced. To address this problem, we would like threads in the same warp to be responsible for adjacent output tiles that are only 4×4 in size. This size would allow each of these threads to issue vector stores of four-element chunks that are all adjacent to each other, resulting in a fully coalesced store transaction. To achieve this goal, we replace each thread’s 8×8 output tile with four different 4×4 output tiles. Fig. 15.10 shows how the thread-level output tiles can be rearranged such that threads in the same warp process adjacent 4×4 output tiles. On the left side of the figure, the encompassing block-level output tile is logically partitioned across the different warps in the block. One can think of each partition as a warp-level output tile. For example, assume that we have a 128×128 block-level output tile and a block of 256 threads or eight warps. The warps of the block are organized into a 2×4 arrangement, and each warp takes a 64×32 sub-tile of the block-level output tile. We will refer to each one of these 64×32 sub-tiles as a warp-level output tile. In the middle of Fig. 15.10, the warp-level output tile is logically partitioned into four quadrants, and each thread in the warp takes a 4 × 4 sub-tile from each quadrant. For example, if the warp-level output tile’s size is 64×32, then each quadrant’s size is 32×16. If we organize the 32 threads in the warp into an 8×4 arrangement, then each thread receives a 4×4 output tile from each quadrant. The right side of Fig. 15.10

15.6 Eliminating bank conflicts Another challenge with making threads responsible for computing large output tiles is that it causes them to access shared memory in a strided manner. Recall from Chapter 6 that threads accessing shared memory in a strided manner can cause bank conflicts. Recall that each warp is organized into an 8 × 4 configuration so the first 4 threads will be loading from identical locations of the block-level tile of A in the shared memory. The first element loaded by threads 0 to 3 is the first element of row 0. This element has a linear index of 0, which we will assume is located in bank 0.

The first element loaded by threads 4 to 7 is the first element of row 4. Assuming the block-level input tile in shared memory has a width of 8, the linear index of this element is 4 × 8 + 0 = 32, which is also located in bank 0 (32 mod 32). Similarly, the first element loaded by threads 8 to 11 is the first element of row 8, which has a linear index of 8 × 8 + 0 = 64 and is also located in bank 0 (64 mod 32). Although we have focused only on the first elements loaded by the four-thread groups, the second elements loaded by the four-thread groups in each warp all fall into bank 1. In fact, all the corresponding elements loaded by all the 8 four-thread groups are located in the same bank, causing 8-way bank conflicts for all accesses. As we discussed in Chapter 6, one way to eliminate bank conflicts is to rearrange the layout of the data in shared memory, padding a matrix with additional columns. 15.7 Occupancy considerations We have seen that using large tiles increases the arithmetic intensity of the matrix multiplication kernel which improves its performance. However, using large tiles puts pressure on the SM resources, particularly the shared memory used to hold the blocklevel input tiles and the register file used to hold the thread-level input strips and thread-level output tiles. The pressure on these resources has a significant impact on the occupancy of threads on the SM. The pressure on the shared memory resources can easily be alleviated. Recall from Section 15.2 that when the first input tile has dimensions m × k, the second input tile has dimensions k × n, and the output tile has dimensions m × n, the arithmetic intensity is 0.5 · m · n/(m + n). Interestingly, the arithmetic intensity is independent of k. Hence, the pressure on shared memory can be mitigated by using a smaller value of k without affecting the arithmetic intensity. For example, if m = n = 128, we can set k to 8. In this case, A_s and B_s would have sizes of 128 × 8 elements and 8 × 128 elements, respectively, which amounts to 4 KB each. This amount of shared memory usage does not limit occupancy on a modern GPU. On the other hand, the pressure on the register file remains high. For example, if each thread is responsible for an 8 × 8 thread-level output tile, it needs 64 registers to store the output tile alone. If register tiling is applied to the thread-level input tiles, then each thread needs an additional eight registers for each of the input strips, bringing the total to 80 registers. This number does not even include all the other registers needed to store local variables and temporary values used throughout the computation. In fact, loop unrolling, which we have applied aggressively, further exacerbates the register usage because it increases the number of temporary values that need to be stored throughout the computation. This high demand for registers makes the number of registers in the SM the main limiting factor for occupancy. In practice, such matrix multiplication kernels use the maximum number of registers per thread that they are allowed to use, which is 255 registers per thread on a modern GPU. With a typical SM’s register file having a capacity of 64k registers, the number of threads per SM is limited to 256 threads. This limit explains why we chose our thread block size to be 256 threads per block in Section 15.3. Accordingly, each SM executes only a single thread block with 256 threads, which is only 12.5% of the SM’s maximum occupancy of 2048 threads.

Although executing with such low occupancy is not usually desired, the extreme benefit of register tiling to increase arithmetic intensity makes it worthwhile. However, executing with low occupancy has two major drawbacks that need to be overcome. The first drawback is that the GPU executes fewer threads which are capable of issuing fewer memory access instructions to fully utilize the memory bandwidth. We overcome this drawback by having each thread issue larger memory accesses using vector loads and stores, as we saw in Section 15.3. The second drawback of executing with low occupancy is that the SM has fewer threads available to tolerate long-latency instructions. We overcome this drawback with aggressive loop unrolling, as we saw in Section 15.3. In particular, as mentioned in Chapter 6, loop unrolling eliminates long-latency branch instructions and exposes more independent instructions that the compiler can schedule to increase the distance between long-latency instructions and their users. With proper loop unrolling and instruction scheduling, much of the compiled kernel code becomes a sequence of independent fused-multiply-add instructions that fully-utilize the SM’s cores with little need to stall. The remaining long-latency operations that we need to be concerned with are the memory accesses and barrier synchronizations. Normally, for a compute-bound kernel that has high arithmetic intensity, we do not need to be concerned with the latency of memory accesses because they can be overlapped with the compute instructions. For example, while one thread block on the SM waits for its input tiles to be loaded from global memory to shared memory, another thread block could be fully utilizing the SM cores with its unrolled sequence of independent fused-multiply-add instructions. However, since the occupancy in our case is limited to a single thread block per SM, this overlap does not happen. Instead, a thread block executes on an SM in two phases: a memory-bound phase where the input tiles are loaded while the compute cores are idle, and a compute-bound phase where the computation is performed while the memory access hardware is idle. In the absence of multiple thread blocks to hide the memory access latency, we must resort to software optimizations for overlapping these two phases. One such optimization is software pipelining, which is discussed in Section 15.8.

## Software pipelining {#sec-15-8}

15.8 Software pipelining We saw in Section 15.7 that in the matrix multiplication kernel we have implemented so far, a single thread block executes on each SM in two phases: a memory-bound phase and a compute-bound phase. In each phase, either the compute resources or the memory resources will be underutilized, so the speed of execution will not reach its full potential. To better utilize the GPU resources, we would like to overlap the memory-bound and compute-bound phases to hide the long latency of the memory instructions behind the execution of the compute instructions. This overlap can be achieved with software pipelining.

Fig. 15.12(a) illustrates the interleaving of instructions when performing tiled matrix multiplication without software pipelining, and Fig. 15.13(a) shows the corresponding timing diagram. First, instructions are executed to load the input tiles A0 and B0 from shared memory. Next, a __syncthreads() is executed to ensure that all threads finish loading their part of the data before any computation is performed. After that, the contribution of A0 and B0 to the output tile, referred to as C0, is computed. Next, another __syncthreads() is executed to ensure that all threads finish using A0 and B0 before loading new input tiles in their place. Following the sec 365

ond synchronization, the process repeats with the next pair of input tiles, A1 and B1, loaded to shared memory. An important observation from Fig. 15.12(a) and Fig. 15.13(a) is that while the input tiles are being loaded from global memory, there are no floating point operations being performed. In other words, the memory access hardware is busy while the floating point ALUs remain idle. On the other hand, when the contribution to the output tile is being computed, there is no data being loaded from global memory. In other words, the floating point ALUs are busy while the memory access hardware remains idle. Ideally, we would like to interleave the instructions that load the data from global memory with those that perform floating point computations. This interleaving would place independent fused-multiply-add instructions after long-latency memory access instructions, making sure that the memory access hardware and the floating point ALUs remain busy all the time. However, the compiler is prevented from interleaving the memory access instructions and the floating point arithmetic instructions together because of the presence of a barrier synchronization operation that separates the data loading and computation stages. Looking back at Fig. 15.12(a), we observe that the barrier synchronizations that separate loading a pair of input tiles from computing those tiles’ contributions enforce a true dependence. That is, we must wait for data to be loaded before we can start using it. On the other hand, the barrier synchronizations that separate computing the contribution of a pair of tiles from loading the next pair of tiles enforces a false dependence. That is, these two activities can execute independently, but they are prevented from doing so because the same memory location that holds the old pair while computing is being used to write the new pair. Recall from Chapter 6 that we can eliminate a barrier synchronization that enforces a false dependence by using the double-buffering optimization. That is, we can use a different memory buffer for loading the next pair of input tiles from the memory buffer holding the current pair of input tiles being used for computation. By doing so, we eliminate the false dependence and no longer need the barrier synchronization, as shown in Fig. 15.12(b). Rather than allocating a different buffer for each iteration, we can reuse buffers such that only two buffers are needed: one for the even iterations and one for the odd iterations. While eliminating the barrier synchronizations paves the way for interleaving the memory access instructions with the floating point arithmetic instructions, an obstacle still exists. The instructions to be interleaved occur in different loop iterations which prevents the compiler from interleaving them. To overcome this obstacle, we apply software pipelining where the code of the loop is rearranged such that the i th loop iteration computes the contribution of the i th pair of tiles while loading the (i + 1)th pair of tiles. Upon rearranging the loop in this way, the compiler is then able to interleave the memory access and floating point arithmetic instructions, as shown in Fig. 15.12(c) and Fig. 15.13(b), thereby increasing the independent instructions scheduled consecutively and reducing the warp’s need to stall. While software pipelining is effective at interleaving memory access instructions with compute instructions to overlap their execution, it relies on the success

of the compiler at estimating the latency of the instructions when applying instruction scheduling. However, the compiler has limited knowledge of the conditions that the code will encounter as it executes. Alternatively, we could delegate the interleaving of memory access instructions with compute instructions to the hardware. One technique for doing so is to program some warps to perform the memory accesses while other warps to perform the computation. In this case, the hardware will automatically interleave these operations as it schedules the warps to execute in a multithreaded manner. This technique is referred to as warp specialization. Yet another way to delegate the interleaving to the hardware is to use specialized hardware support for transferring data between global memory and shared memory in the background. This kind of support is discussed in Section 15.9.

## Specialized software and hardware support {#sec-15-9}

15.9 Specialized software and hardware support Due to the prevalence and importance of matrix multiplication in GPU computing, it is common for hardware vendors to provide specialized libraries with highly optimized matrix multiplication routines that embody the optimizations introduced in this chapter. For example, NVIDIA provides multiple CUDA libraries such as cuBLAS [1], cuDNN [2], and CUTLASS [3] for this purpose. cuBLAS is a library that provides a GPU implementation of the standard BLAS API for basic linear algebra, including matrix multiplication. cuDNN is a library that provides routines for implementing deep neural networks on GPUs, which perform matrix multiplication underneath. CUTLASS is an open source library for implementing matrix multiplication at different levels and scales, which makes it easier to incorporate matrix multiplication as a building block in a larger kernel. More recently, programming interfaces like cuTile allow developers to write array-based code and use the compiler to perform advanced optimizations by taking advantage of the special properties of tensors. With these libraries and programming interfaces, GPU programmers typically do not implement matrix multiplication from scratch. Nevertheless, learning about the advanced optimizations applied to matrix multiplication is a useful exercise in understanding the underlying techniques, which may be applied in other contexts as well. GPUs also provide dedicated hardware support for matrix multiplication that can be used by the compiler, programmed directly with a special API, or more commonly, used by calling routines from libraries such as cuBLAS, cuDNN, or CUTLASS. For example, beginning with the Volta architecture, some NVIDIA GPUs come with tensor cores which are special-purpose cores that each perform a small matrix multiplication operation in a single instruction. Reducing the number of instructions required to perform matrix multiplication eliminates bottlenecks due to limited instruction decoding and processing throughput. Furthermore, tensor cores achieve extremely high matrix multiplication throughput by taking advantage of advanced warp-level hardware features for exchanging register contents, and by using lower-precision floating-point arithmetic units.

Before the Hopper architecture, tensor cores could be programmed with the Warp Matrix Multiply and Accumulate (WMMA) instructions, which were limited to individual warps. The Hopper architecture introduced a Warp Group Matrix Multiply Accumulate (WGMMA) instruction that enables a group of warps to work together on a larger matrix multiplication using tensor cores. Moreover, WGMMA can take input operands directly from shared memory, alleviating the register pressure. The WGMMA instruction can execute asynchronously with other instructions, reducing the reliance on the compiler to schedule the instructions for overlapping the long latency instructions. Additionally, the Blackwell architecture introduces a new tensor memory (TMEM), which is an on-chip memory for storing the inputs and outputs of tensor core operations, further reducing the register pressure. Interested readers are referred to the literature for details of the design and use of WGMMA and TMEM. As hardware support such as tensor cores elevates the compute throughput for matrix multiplication, the throughput of matrix multiplication can become limited by the rate at which data can be fetched from and stored to shared memory and global memory. While global memory bandwidth and shared memory bandwidth play fundamental roles in moving data to and from the arithmetic units, instruction processing overhead for data movement and the impact of register usage on occupancy significantly affect the rate of data movement. For example, as we saw in Section 15.5, an effective hardware support for higher data throughput is vector stores. Using an appropriate output tile configuration, each thread can store more data using the same number of instructions, reducing instruction processing overhead and improving memory coalescing. However, moving data between global memory and shared memory using vector loads and stores still requires two steps: loading the data from one memory into registers followed by storing the data from registers to the other memory. This two-step process increases the usage of the register, not to mention the instruction execution overhead. Recent NVIDIA GPUs support LDGSTS instructions that load vector data directly from global memory to shared memory without going through registers. Using one instead of two instructions also reduces instruction processing overhead. LDGSTS instructions allow more effective overlap of memory accesses with computations by allowing the hardware to perform the memory access asynchronously in the background, without the need for the compiler to interleave the memory access instructions with compute instructions. The NVCC compiler can automatically detect a code sequence formed by a vector load from global memory into registers followed by vector store to the shared memory in kernel code and generate one single LDGSTS instruction. Programmers can also call the cuda::memcpy_async function in the libcu++ library from their kernel code to use the LDGSTS instruction. Interested readers are referred to the literature for code examples and important details such as data alignment. Beginning with the Hopper architecture, NVIDIA GPUs also come with a Tensor Memory Accelerator (TMA), which supports asynchronous transfer of entire tensors between global memory and shared memory without using intermediate registers. TMA can be viewed as a generalization of the LDGSTS instruction from 1D vectors into multidimensional tenors. TMA can be used via the cuda::memcpy_async API, and also by calling routines from libraries such as cuBLAS, cuDNN, or CUTLASS that use it.

## Summary {#sec-15-10}

15.10 Summary In this chapter, we have seen how many of the optimizations introduced in Chapter 6 can be applied in the context of matrix multiplication to achieve an advanced and highly optimized matrix multiplication kernel. We observed that using large output tiles increases the arithmetic intensity of the kernel to make it compute bound, and applied thread coarsening to achieve these large output tile sizes. After overcoming the global memory bandwidth bottleneck, we applied register tiling to the input tiles to also overcome the shared memory access latency. We rearranged the mapping of threads to data to ensure coalesced store operations when writing the output tiles from registers to global memory. We also added padding to one of the shared memory input tiles to avoid bank conflicts. We observed that the excessive use of registers results in very low occupancy, and applied mitigations to overcome the drawbacks of low occupancy. Using vector loads and stores ensures that threads issue enough memory accesses to utilize the memory bandwidth. Aggressive loop unrolling ensures that cores have enough independent compute instructions to utilize the floating point ALU throughput. Software pipelining or warp specialization ensure that the memory access and compute instructions are interleaved such that the latency of the memory access instructions can be overlapped with the execution of the compute instructions. The optimizations discussed in this chapter are readily available in libraries such as cuBLAS, cuDNN, and CUTLASS. These libraries also use specialized hardware support such as tensor cores, tensor memory, asynchronous memory copies, and the tensor memory accelerator. Programmers typically use these highly optimized libraries and do not implement matrix multiplication from scratch. Still, matrix multiplication is an excellent use case for demonstrating many of the optimizations we have learned in this book.

Wavefront parallelism is an algorithmic technique for exploiting data parallelism in applications with data dependencies along space and/or time dimensions. In this chapter, we study wavefront parallelism in the context of dynamic programming applications. Dynamic programming represents a class of problems that can be solved by dividing a problem into smaller sub-problems. The solution to the original problem can be found by assembling the solutions found for the sub-problems. Parallelizing dynamic programming algorithms on GPUs entails interesting challenges in terms of hardware utilization and synchronization across threads. In this chapter, we discuss these challenges and present software techniques that address them efficiently.
