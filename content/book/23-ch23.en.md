After computing the new value at its grid point, each thread calculates its grid point’s residue as the difference between the new value and the old value (line 13). To calculate the L2 norm, the squares of the residues need to be summed up across all threads in the grid. Fig. 23.2 illustrates the modeled system and how it can be partitioned across multiple GPUs. We assume that the system is modeled as a structured grid, where the spacing between grid points is constant in each direction. This assumption allows us to use a 2D array to represent the system, where each element stores the state of a grid point, as we discussed in Chapter 8. The physical distance between adjacent elements in each dimension can be represented by a grid spacing variable. In the 2D array, we assume that the data is placed in the memory space in the row-major layout, where x is the lowest dimension followed by y. That is, all elements with y = 0 are placed in consecutive memory locations according to their x coordinate, followed by all elements with y = 1, etc. When one uses multiple GPUs, it is common to divide the input data into several partitions, called domain partitions, and assign each partition to a different GPU FIGURE 23.3 Values available to each GPU before and after computation.

in the cluster. With the row major layout, it is natural to partition the system across GPUs along the y-dimension, giving each GPU a contiguous set of rows. This partitioning is illustrated in Fig. 23.2 where the grid points that each GPU is responsible for computing are indicated by different colors and separated by solid lines. Such partitioning ensures that each GPU’s partition is contiguous in memory according to the row-major layout. Recall that to compute the new value at each grid point, the old values at the neighboring points are needed. Hence, for a GPU to compute the new grid point values at its partition’s edge, it needs the old values of the grid points at the edges of the adjacent partitions. These grid points, called halo points, are indicated in Fig. 23.2 by the dotted lines. For example, for GPU 1 to compute the new values of the grid points in its partition, it needs the old values of all these grid points as well as the old values of the bottom row of GPU 0’s partition and the top row of GPU 2’s partition. The span of input rows needed as input by GPU 1 is indicated by ny. The first and last rows in the span are the halo points, used only as input, whereas the middle ny − 2 rows are both inputs and outputs. Fig. 23.3 further illustrates the values available to each GPU before and after computing the grid point values in its partition. Before computing, the GPU needs the values of the halo rows as shown in Fig. 23.3(a). After computing, the values at its halo rows become out of date as shown in Fig. 23.3(b). The new values at the halo rows are computed by the other GPUs that are responsible these rows. Hence, before proceeding to the next iteration, a GPU needs to obtain the updated values of the halo rows from the GPUs computing the adjacent partitions. For example, GPU 1 needs to copy its top halo row from GPU 0 and its bottom halo row from GPU 2. Simultaneously, GPU 1 needs to send its top row to GPU 0 and its bottom row to GPU 2. This sending and receiving of halo rows between adjacent GPUs is referred to as halo exchange. Here, we observe another benefit of applying a 1Ddomain decomposition across the y-dimension when using the row-major layout. The halo rows that need to be copied from one GPU to another are contiguous in memory, which simplifies the copy operation during halo exchange. One drawback of this 1D domain decomposition scheme is that depending on the shape of the domain and the number of GPUs, large volumes of data may need to be communicated between GPUs. For example, if the domain is very wide, each GPU would need to communicate an entire row of the domain which can be expensive. Alternatively, one could use a 2D domain decomposition where each GPU takes a 2D tile of the domain. A 2D domain decomposition reduces the surface to volume ratio, thereby reducing the amount of data that needs to be communicated. However, a 2D domain decomposition would require each GPU to communicate with four other neighboring GPUs instead of just two, and some of the data that needs to be communicated would not be contiguous. To keep the examples in this chapter simple, we focus on the described 1D domain decomposition. In summary, every iteration of the multi-GPU Jacobi iterative method consists of two phases: a computation phase, where the new values at the grid points are computed, and a communication phase, where the new values at the halo rows are exchanged between GPUs computing adjacent partitions. Moreover, since the L2 norm needs to encompass all the grid points in all the partitions, the communication phase additionally includes a reduction operation that reduces the grid-wide L2 norms computed by each GPU. Each of MPI, NCCL, and NVSHMEM provide their own mechanisms for exchanging data between GPUs. We will see how these operations can be done with each programming model throughout this chapter.

The next step is to perform the halo exchange. The halo exchange requires the MPI processes to communicate with their neighbors to send their new boundary grid point values to each other. Such communication can be done with MPI point-to-point communication, which involves exchanging message between two communicating processes. MPI provides many different types of point-to-point communication routines. In our code example, we use the MPI_Sendrecv() routine. To understand what MPI_Sendrecv() does, let us first look at the more basic point-to-point communication routines that MPI provides. The most basic point-to-point communication routines in MPI are MPI_Send() and MPI_Recv(), where a source process calls the MPI_Send() function to send data to a destination process, and the destination process calls the MPI_Recv() function to receive that data from the source process. This is analogous to a caller dialing a call and a receiver answering a call in a telephone system. Because both sides of the communication must participate for the communication to take place, such point-to-point communication is referred to as two-sided communication. First, each process identifies the neighbor process at its top (line 11) and the one at its bottom (line 12). Rather than simply computing rank - 1 and rank + 1, the code uses a wrap-around strategy where the topmost rank treats the bottommost rank as its top neighbor, and vice versa. This wrap-around strategy is often referred to as the periodic boundary condition technique for modeling a large system by simulating only a small portion of it without introducing a disproportional amount of edge effects. Such boundary conditions require special handling of the top and the bottom ranks since they would not have a top neighbor and bottom neighbor, respectively, to communicate with.

The first call (lines 13-15) sends the top boundary row, which starts at output + nx, to the top neighbor, and receives the bottom halo row, which starts at output + (ny - 1)\*nx, from the bottom neighbor. It is important to note that the output and input pointers passed to the MPI_Sendrecv function are pointers to the GPU device memory. Passing GPU device memory pointers to MPI functions is possible with CUDA-aware MPI. If the MPI implementation used is not CUDA-aware, the programmer would have needed to copy the data from device memory to host memory and invoke the MPI communication function on the host memory array. In contrast, CUDA-aware MPI implementations are aware of the CUDA programming model and are designed to allow communication functions to be invoked on CUDA global memory arrays directly. Allowing send and receive functions to work directly on the device arrays eliminates the need for cudaMemcpy calls in the source code and thus minimizes the bloat to the host code size as well as the added communication latency. Most MPI implementations (e.g., MPICH [6], OpenMPI [7], MVAPICH2 [8]) are designed to be CUDA-aware and are built with this feature enabled. After the halo exchange, the host code needs to calculate the L2 norm to identify if the system has significantly changed and we need to continue iterating. Each GPU has already computed the square of the L2 norm of its own partition’s residual. However, we still need to sum up these L2 norm squares across all the partitions. In other words, we need to perform a reduction operation across all the MPI ranks, where each rank contributes its own partition’s L2 norm square. Such a reduction across ranks can be done with MPI collective communication. In contrast with MPI point-to-point communication, such as MPI_Sendrecv, which involves communicating between two ranks, MPI collective communication involves communicating between all ranks in the communicator. The commonly used types of MPI collective communication are barrier, broadcast, reduce, gather, and scatter. We will not elaborate on all types of MPI collective communication functions but encourage the reader to read the MPI programming guide [1] for the details of these functions. In general, collective communication functions are highly optimized by the MPI runtime developers and system vendors. Using the collective communication functions usually leads to better performance as well as readability and productivity than trying to achieve the same functionality with sequences of send and receive calls. The MPI collective communication function that we are interested in for computing the L2 norm is MPI_Allreduce. The MPI_Allreduce function takes a buffer of values from each rank, reduces the buffers into a single buffer, and gives a copy of that buffer to each rank. neighbors, and repeats. While this strategy is very simple, it is not very efficient. The reason is that this strategy forces the system to be in one of two modes, where each mode only utilizes part of the system. In the first mode, all processes are performing computation using the GPUs. During this time, the communication network is not used. In the second mode, all processes are exchanging halo data with their top and bottom neighbors using the communication network. During this time, the GPU compute hardware is not well utilized. Ideally, we would like to achieve better performance by utilizing both the communication network and GPU compute hardware all the time. This improved utilization can be achieved by dividing the computation tasks of each process into two stages, as illustrated in Fig. 23.12. During the first stage (Stage 1), each process calculates its boundary rows that are needed as halo cells by its neighbors in the next iteration. Fig. 23.12 shows the boundary rows computed in this stage as colored rows. For example, GPU 1 calculates its top and bottom boundary rows, which are the halo rows of GPU 0 and GPU 2, respectively. The rationale is that these boundary rows are needed by the neighbors for the next iteration. By calculating these boundary rows first, the data can be communicated to the neighbors in the second stage while the rest of their internal grid points are calculated. During the second stage (Stage 2), each process performs two activities in parallel. The first is to communicate its new boundary values to its neighbor processes. The second activity is to calculate the rest of the data in the partition. If the communication activity takes a shorter amount of time than the calculation activity, we can hide the communication delay and fully utilize the computing hardware most of the time. This is usually achieved by having enough rows in the internal part of each partition to allow each process to perform enough computation to hide the communication. are not overlapped, the entire computation is performed by the compute hardware while the communication network is idle. Subsequently, the top and bottom halos are exchanged over the communication network while the compute hardware is idle. The L2 norm reduction is also performed. In contrast, in Fig. 23.13(b), the top and bottom grid points are computed distinctly from the internal grid points, and the top and bottom halo exchanges are initiated as soon as the corresponding grid points are computed. For GPUs with a sufficient amount of compute resources, grid points in the three categories can be computed concurrently. However, priority should be given to the boundary grid points in order to initiate the halo exchange as soon as possible. Importantly, the internal grid points continue to be computed while the halo exchanges are performed. This overlap between computing the grid points and performing the halo exchanges ensures that both the compute hardware and communication network are utilized simultaneously, resulting in the overall execution to finish sooner. Inevitably, reducing the L2 norm cannot be overlapped because it depends on all the grid points being computed. Accomplishing this kind of overlap between communication and computation requires splitting the Jacobi kernel call into separate kernel calls for computing the boundary elements and the internal elements. For example, we can split the kernel call into three different calls: one for the top boundary row, one for the bottom boundary row, and one for the internal elements. In this way, the halo exchanges can be initiated as soon as the kernels processing the boundary rows are done. To execute these three kernels concurrently and synchronize the communication activities with each of them independently, we need to use an important feature of the CUDA programming model which is CUDA streams. In CUDA, a stream is an ordered sequence of CUDA operations. These operations could include kernel calls and memory copies, among other things. All operations in the same stream are done sequentially according to the order in which they are placed into that stream. On the other hand, operations in different streams may be executed concurrently without any ordering constraint. Hence, to get the three aforementioned Jacobi kernels to execute concurrently, we should insert them into three different streams, which starts with the creation of stream objects in the following code: cudaStream_t topStream, bottomStream, internalStream; cudaStreamCreate(&internalStream); cudaStreamCreate(&topStream); cudaStreamCreate(&bottomStream);

The first line declares three stream objects of type cudaStream_t. The stream objects are named topStream, bottomStream, and internalStream, referring to the streams that will contain the calls to the kernels that process the top boundary row, the bottom boundary row, and the internal rows, respectively. The next three lines create these streams by calling cudaStreamCreate and passing to it a pointer to the stream object. Each call to cudaStreamCreate() creates a new stream and initializes the state of that stream. To insert a kernel call into a particular stream, the stream object can be passed as a configuration parameter for the kernel call. Recall from Chapter 2 that a kernel call takes two required configuration parameters in triangle brackets, the first being the grid dimension and the second being the block dimension. Also recall from Chapter 5 that the kernel call takes an optional third configuration parameter which is the size of the dynamically allocated shared memory. If not specified, the value is 0 by default. Similarly, the kernel call also takes an optional fourth configuration parameter which is the stream into which the kernel call is to be inserted. If not specified, the kernel call is inserted into a default stream. The following code shows how a kernel call can be inserted into a specific stream: kernelName<<<dimGrid, dimBlock, 0, myStream>>>(...)

This code inserts a call to kernel kernelName with a grid dimension specified in dimGrid, a block dimension specified in dimBlock, and zero dynamically allocated shared memory, and inserts itself into the stream specified in myStream. Note that returning from the call does not mean that the kernel has been executed. It simply means that the kernel has been inserted into the designated stream. The execution of the host code will continue with the following code as soon as the kernel has been inserted into the stream. The fact that a kernel call in the host code inserts the kernel into a stream, rather than actually executing the kernel, makes the CUDA kernel calls asynchronous. Furthermore, the continued execution of the host code after the kernel call does not mean that the corresponding thread grid has completed executing the kernel. It does not even mean that the thread grid has started executing the kernel. It simply means that the kernel has been inserted into the designated stream and a grid will eventually be launched to execute the kernel after all preceding operations in the stream have completed their execution.

To fully understand the concept of pinned memory and why it is needed for asynchronous copies, we first need to know a little more background on the memory management in operating systems. In a modern computer system, the operating system manages the memory address spaces of many applications simultaneously. Each application has access to a large and logically consecutive address space called a virtual address space. In reality, the system only has a limited amount of physical memory that needs to be shared among all running applications. This sharing is done by partitioning the virtual address spaces of applications into virtual pages and mapping these pages to physical pages in the physical memory. Mapping virtual pages to physical pages achieves multiple goals. One goal is to ensure that processes cannot access each other’s pages inphysical memory without explicit sharing arrangements. They can only access the physical pages that are mapped into their own virtual address space. Another goal is to accommodate situations when there is higher demand for memory than the amount of physical memory available. In such cases, only the most actively used virtual pages are mapped to physical pages while the others are placed on disk. As part of this process, the operating system may need to ``page out'' some of the pages from the physical memory to mass storage such as disks to make room for other pages. Therefore, an application may have its data paged out of physical memory at any time during its execution. The implementation of cudaMemcpy() uses a type of hardware called a Direct Memory Access (DMA) device. When a cudaMemcpy() function is called to copy between the host and device memories, its implementation uses a DMA to complete the task. On the host memory side, the DMA hardware operates on physical addresses. That is, the operating system needs to give a translated physical address to the DMA. However, there is a chance that the data may be paged out before the DMA operation is complete. The physical memory locations for the data may be re-assigned to other data corresponding to a different virtual memory location. In this case, the DMA operation can be potentially corrupted since its data can be overwritten by the paging activity. A common solution to this data corruption problem is for the CUDA runtime to perform the copy operation in two steps. For a host-to-device copy, the CUDA runtime first copies the source host memory data into a ``pinned'' memory buffer, which means that the memory locations are marked so that the paging mechanism will not page out the data. It then uses the DMA device to copy the data from the pinned memory buffer to the device memory. For a device-to-host copy, the CUDA runtime first uses a DMA device to copy the data from the device memory into a pinned memory buffer. It then copies the data from the pinned memory buffer to the destination host memory location. By using an extra pinned memory buffer, the DMA copy will be safe from any paging activities. There are two problems with this approach. The first problem is that the extra copy adds delay to the cudaMemcpy() operation. The second problem is that the extra complexity involved leads to a synchronous implementation of the cudaMemcpy() function. That is, the host cannot continue to execute until the cudaMemcpy() function completes its operation and returns because the host needs to be involved in the memory copy operation. In order to support asynchronous copies such as cudaMemcpyAsync(), we need to eliminate the step where the host copies the data from a regular memory buffer to a pinned memory buffer. For this reason, the cudaMemcpyAsync() function requires that the host memory buffer passed to it be already allocated as a pinned memory buffer.

## Multi-GPU stencil with NCCL {#sec-23-4}

method described in Section 23.3 is effective at overlapping computation and communication by using concurrent asynchronous kernel calls, memory copies, and CUDA streams. However, the implementation still has some synchronization points that introduce inefficiency. If we look back to the code in Fig. 23.14, we observe that the host thread calls cudaStreamSynchronize (lines 27 and 31) before the calls to MPI_Sendrecv to ensure that the kernels computing the top and bottom boundary rows are complete before initiating the network communication for the halo exchange. During this time, the cudaStreamSynchronize function blocks the host thread from executing any of the subsequent statements in the host code. This need to involve the host thread in the synchronization means that the host cannot be used to perform other useful work. This inefficiency can be overcome if we free the host thread from the burden of synchronizing between CUDA operations such as kernel calls and communication operations. In other words, if the communication operations themselves could be placed inside the streams, then the stream mechanism can simply be used to initiate the communication operations as soon as the operations that they depend on are complete, and without involving the host thread. This desire to perform the communication operations within the context of the CUDA streams is one motivation behind the NVIDIA Collective Communications Library (NCCL) [2]. NCCL is a library that provides various inter-GPU communication primitives. It supports both point-to-point communication, such as send and receive primitives, and collective communication, such as reduce, broadcast, scatter, and gather primitives. While the communication primitives in NCCL resemble those in MPI, an important difference is that NCCL communication primitives run on the GPU, not the host CPU, and can be placed inside of CUDA streams. Hence, using NCCL frees the host thread from having to serve as a synchronizing intermediary between kernel calls and communication primitives. Another benefit of NCCL communication primitives is that they are highly optimized for multi-GPU communication, both within and across nodes, in a topology-aware manner. NCCL thus frees developers from the burden of optimizing their communication routines for specific systems and interconnects. NCCL supports multiple interconnect technologies such as PCIe, NVLINK, InfiniBand Verbs, and sockets. NCCL is not a complete replacement for MPI, but rather, a library that can be used in conjunction with MPI to enhance multi-GPU communication. To use NCCL in conjunction with MPI, we must set up and tear down the NCCL communication system similar to how we set up and tear down the MPI communication system. NCCL is referred to as two-sided communication. The communication is two-sided because for a process to send data to or receive data from another process, the two processes have to both be executing corresponding primitives. In the case of MPI, the call to MPI_Sendrecv in the sending process must have a corresponding call to MPI_Sendrecv in the receiving process. In the case of NCCL, the call to ncclSend in the sending process must have a corresponding call to ncclRecv in the receiving process. The reason that both processes have to be involved is that the sending process specifies where the communicated data is coming from, whereas the receiving process specifies where the communicated data should be placed after being received. During actual execution, the sending and receiving processes need to wait for each other to reach these calls to initiate the communication, which incurs additional latency. An alternative form of communication that is commonly used in parallel computing is one-sided communication. In one-sided communication, a process can send data to or receive data from another process without involving the other process. The process directly accesses the other process’ address space with put operations that store data to the other process’ address space, or get operations that load data from the other process’ address space. The ability to directly access parts of another process’ address space without waiting for the other process to become available reduces the latency of data communication. It also enables the communication to be initiated by threads executing on the device since matching send and receive calls is not scalable to hundreds of thousands of threads executing on the device, but one-sided put and get operations are. A commonly used library for one-sided communication is OpenSHMEM [9]. NVIDIA provides an implementation of OpenSHMEM for clusters of GPUs called the NVIDIA OpenSHMEM Library (NVSHMEM) [3]. The reader may wonder how threads in a process initiating a put or get operation can know the address of the accessed data object in the target process’ address space. In two-sided communication, this address is specified by the matching call executed by the target process, whereas in one-sided communication, the initiating process needs to specify it. Each process allocates a portion of its address space to locally accommodate the symmetric heap, and all processes allocate corresponding memory objects within their address spaces at the same offset in their respective local instances of the symmetric heap. We comment on the implications of launching only one kernel for both the computation and communication in each Jacobi iteration later in this section. After inserting the kernel that performs the computation and the halo exchange into the stream, we need to guarantee that the boundary values have arrived at the target process before proceeding to the next iteration. In the MPI-based implementation in Fig. 23.14, this guarantee comes from the fact that the calls to MPI_Sendrecv are blocking, which means they do not return until the data have arrived. Therefore, by the time all processes have reached the MPI_Allreduce in the timeline in Fig. 23.15, we know for sure that all halo exchange data have been received. In the NCCL-based implementation in Fig. 23.20, this guarantee comes from the fact that we synchronize on the ncclSend and ncclRecv events in the appropriate streams. The cudaStreamWaitEvent() calls before the end of the iteration guarantee that the halo exchange data have arrived for each process before the L2 norm is reset for the next iteration. In the NVSHMEM-based implementation in Fig. 23.25, the boundary values are sent by the same kernel that calculates the grid points. The kernel will complete as soon as all the launched threads complete their work in computing the grid point values and sending the halo data. Synchronizing on the stream only guarantees that the kernel has finished its computation and sending the data; it does not guarantee that the data has been received. To ensure that data have been received, we need to callnvshmemx_barrier_all_on_stream, the NVSHMEM API function that provides suchguarantee, on the same stream as the kernel (line 18). This call makes all PEs wait at the barrier until all the NVSHMEM memory access operations initiated by any preceding kernels in the stream have completed. Therefore, when all the processes proceed to the next iteration, we know for sure that all halo exchange data have been received and it is safe to proceed. Using NVSHMEM to perform put operations of the halo values directly from the kernel has two key advantages. The first advantage is that it automatically overlaps computation and communication. With MPI and NCCL, the kernel needs to be terminated before the communication could be started. For this reason, we have to separate the computation of the boundary values and the internal values into different kernels so that we can wait for only the kernel computing the boundary values before initiating the communication in parallel with the kernel computing the internal values. In NVSHMEM, it is unnecessary to launch separate kernels and orchestrate the concurrency between them. NVSHMEM allows the halo values to be sent from within some of the GPU threads using the put operation as soon as they are computed, and allows other threads to continue to compute the internal grid point values while the communication initiated by the put operation happens in the background. The second advantage of performing put and get operations directly from within the kernel is that it allows multiple operations to be fused into a single kernel. This advantage is less apparent with our Jacobi iterative method example because there is only one operation, i.e., the stencil operation. However, if the computation consisted of multiple computations with different communications happening in between these computations, then MPI and NCCL would require each of these computations to be executed by separate kernels. On the other hand, NVSHMEM would enable fusing these operations in the same kernel and communicating from within the kernel. Such kernel fusion could reduce the overhead of kernel launches for small kernels, as well as enable keeping data in shared memory and registers if this data is used across the different operations being fused. One subject for potential further study is that the fine-grain manner in which we have used the put operations in the kernel in Fig. 23.23 would perform reasonably well for GPUs connected over NVLINK, which supports low latency and high bandwidth communication. However, for slower interconnects and communication over a network, it would be more efficient to perform fewer and more coarse-grain put operations. NVSHMEM provides an alternative function, nvshmemx_float_put_block where threads in the same thread block can collaborate to execute one coarse-grain put operation. We refer the reader to the NVSHMEM documentation for more information on how to use such more advanced techniques [3].

## Summary {#sec-23-6}

GPUs using three programming models: MPI, NCCL, and NVSHMEM. We use the stencilpattern to show how multiple processes exchange data throughout the execution. Our first implementation uses MPI alone and has each process compute all grid point values in its partition then send the boundary values to neighboring processes after all the computation is done. We then improve on this MPI implementation by computing the boundary values first, then sending the boundary values to neighboring processing while computing the internal grid point values, thereby overlapping computation and communication. Achieving this overlap required the use of CUDA streams to execute different kernels concurrently. We then looked at how the same overlap between computation and communication can be achieved with using NCCL in conjunction with MPI. The advantage of NCCL is that it allows communication operations to be placed inside of CUDA streams, freeing the host from the burden of synchronizing between GPU kernels and MPI communication primitives. Furthermore, the NCCL library is well-optimized for multi-GPU communication, freeing the programmer from the burden of customizing their communication primitives to the underlying system organization and network topology. After that, we looked at how the same overlap between computation and communication can be achieved with NVSHMEM. Unlike MPI and NCCL which rely on two-sided communication, NVSHMEM relies on one-sided communication, which removes the latency of send operations needed to match with corresponding receive operations. Moreover, NVSHMEM put and get operations can be executed from within GPU kernels, which allows kernels to be fused and achieves the overlap between computation and communication transparently. Our comparison of NCCL and NVSHMEM focused on contrasting the hostinitiated two-sided communication in NCCL with the device-initiated one-sided communication in NVSHMEM. However, it is worth noting that these multi-GPU programming APIs continue to evolve and have more and more features in common. For example, NCCL recently added support for symmetric memory and deviceinitiated communication, and may add support for one-sided communication soon. On the other hand, NVSHMEM supports host-initiated communication as well, not just device-initiated communication. Host-initiated communication works well when the data to be communicated are of coarse granularity and can be determined independently of the computation that overlaps with the communication. On the other hand, device-initiated communication is preferred when the data to be communicated are of fine granularity and are determined as part of the computation that overlaps with the communication. While multi-GPU programming is very different from programming GPU kernels, the major programming concepts that we covered (SPMD, ranks, and barriers) all have counterparts in the CUDA programming model. This confirms our belief that by teaching parallel programming with one model well, students can pick up other programming models quickly and easily. We encourage the reader to build on the foundation from this chapter and study more advanced features of MPI, NCCL, and NVSHMEM, and apply them to other important patterns.
